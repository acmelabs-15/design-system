# Publish React support as a separate package

Provide React integration as a separate package around the same Lit components, using @lit/react where appropriate. Peter selected a separate package after the framework-package survey. Package names, peer-version ranges and release coordination were left to the later [documentation/tooling contract](../../spec/SPEC-documentation-tooling.md) and package manifests.

Decided 2026-09-19 by Peter.

React 19 supports custom-element properties and events directly. Wrappers are justified by typed JSX, event mapping and authoring consistency, rather than a claim that React cannot render custom elements. The approved custom-elements-manifest analyzer remains the metadata source; using a wrapper generator must not silently replace it with another analyzer.

For Table, the [clarified consumer-owned scope](0107-tanstack-table-compatibility.md) keeps React cell rendering in the consuming React application. Our component must permit its content, events, references and layout to work correctly. A bridge that runs React cell components through TanStack's Lit renderer is not a selected requirement. Peter also explicitly confirmed TanStack Virtual for both React and Lit virtualization. At the 2026-09-19 decision, final composition still needed browser verification. Server rendering is excluded by the [server-rendering decision](0092-server-rendering.md).

Evidence: [Lit practice review](../research/15-lit-practice-review.md#phase-1-extension-react-and-forms) and [package-layout survey](../research/18-repository-layout.md#phase-1-extension-framework-packages).

The selected declaration-order behaviour requires preserving the intended style-property order across complete React prop sets, including reorder-only renders and removals. The [initial source comparison](../verification/systematization/declaration-order-probe-2026-09-20.json) is followed by [actual React execution](../verification/systematization/style-input-integration-review-2026-09-20.json): with React/React DOM 19.3.0 and @lit/react 1.0.8, the plain wrapper passes 15 of 21 assertions; a wrapper synchronizing the complete style-input order passes all 21, both normally and in Strict Mode. Chromium, Firefox and WebKit produce the same results. The checks include refs, classes, slotted React child identity/state, event mapping, removal/re-addition and unmount.

This establishes a feasible order connection for two styling properties, not the final wrapper API or package certification. At that 2026-09-20 checkpoint, actual package exports/types, compiler/manifest integration, all property kinds and the complete input-order contract remained unverified. Omitted CSS inputs follow the selected [undefined getter rule](0052-layout-spacing-properties.md#omitted-styling-inputs-and-visual-defaults). No production wrapper or package changed in that probe. The later [release record](../releases/0.3.0.md) records package acceptance and its limits.

Peter subsequently selected the [Lit authoring helper](0052-layout-spacing-properties.md#lit-helper-for-ordered-styling-inputs) as the corresponding complete-input path for Lit templates. Both paths retain the same component properties and canonical state. Both paths share the final input/removal/order contract and types. The helper study also exposes a broader late-definition registry requirement at Lit node creation; [global-registry results](../research/15-lit-practice-review.md#lit-helper-lifecycle-and-registry-boundary) do not certify scoped registries or adopted documents for either framework path.

The selected [helper ownership and reassertion rules](0052-layout-spacing-properties.md#external-writes-to-helper-managed-settings) preserve that framework consistency: managed inputs are reapplied on helper renders, matching the tested React wrapper's full-prop writes; direct component-property edits remain effective until a subsequent wrapper/helper render. Unrelated inputs are not automatically cleared by adopting the Lit helper. At that checkpoint, final cross-framework types and complete removal/ownership behavior still needed acceptance. These choices alone do not certify all React paths.
