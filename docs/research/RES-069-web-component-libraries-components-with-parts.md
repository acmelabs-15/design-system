# RES-069: How web component libraries build components with parts

## Question
How do Lit libraries and other web component libraries in wide use build a component with parts: which mechanism links a parent and its parts (the parent reads its slot, context, events, or one closed element), what happens to a part inside a wrapper element, and does any library offer one component as a ready-made form and as a composed form? What do Lit's documentation, its maintainers and the published best practices for web components state for such components, and which names do they use?

Needed by IDEA-003#05 (the choice of the composition architecture of the Lit core, among: parts that get state from their root through context at any depth; parts that their parent finds through its slot as direct children; one closed element that holds all parts), by IDEA-003#06 (where the ready-made component lives), and by the glossary terms for the pattern and its two forms.

This record builds on RES-043 (the mechanisms of Lit and their limits) and on the prototype result of IDEA-003#05. It does not repeat them. It states facts, sources and disagreements. It gives no recommendation and no ranking.

## Answer
Sufficient answer:
1. At least eight libraries in wide use, each with its version, both Lit-based and not. For each, on two or three components with parts: the mechanism that links a parent and its parts, from the source code; what happens when a wrapper element sits between the parent and a part (documented, read from the source, or not known); and whether one component is offered both as a ready-made form and as a composed form.
2. Any web component library that follows the compound pattern of React libraries, with parts that work at any depth below their root, and its mechanism. Which production libraries use `@lit/context` or the Context Community Protocol, and for what.
3. What these sources state as best practice for a parent and its parts: lit.dev; talks, posts and GitHub discussions of the Lit maintainers; web.dev and Google's custom element best practices; the Gold Standard checklist; the Web Components Community Group protocols; Open UI.
4. The names that these sources use for the parts, for the pattern and for the ready-made form.
5. Where the practice of web component libraries differs from the React practice that RES-042 records for Chakra UI.
Limits and contrary evidence are included. The Answer ends with one table.

All checks are of 2026-11-13. Each library was read at one commit of its main branch. The record states facts only.

### 1. The mechanisms that link a parent and its parts
Six mechanisms occur. Most libraries use more than one, and choose by component.

1. **The parent reads its slot or its direct children.** It calls `slot.assignedElements()` (Lit: `@queryAssignedElements`; FAST: the `slotted` directive), or reads `this.children`, and sets state on each part. Parts report back with events. This is the mechanism of candidate B. In this survey most libraries use it for tabs, accordion and stepper: Web Awesome (tab group, stepper, accordion), Shoelace (tab group, menu), Material Web (tabs, list, menu, chip set), Spectrum (tabs, accordion), Fluent UI (tablist, accordion, menu list, radio group, tree), UI5 (every declared slot), Lion (tabs, accordion, steps), Vaadin (tabs, list box, accordion), and the lists of parts in PatternFly Elements and the Red Hat Design System.
2. **The parent searches all its descendants in the light DOM** with `this.querySelectorAll(...)`. Carbon's older components (tabs, content switcher, accordion, progress indicator, dropdown), Ionic (segment, radio group, tabs), Web Awesome and Shoelace (select, radio group, tree), the Red Hat progress stepper, Google's reference `<howto-tabs>`, and GitHub's tab container.
3. **The part finds its parent** with `this.closest(...)` and listens for the parent's events. Ionic (segment button, accordion, radio, picker option) and Calcite.
4. **The part announces itself with a bubbling event**, and the nearest parent on the path registers it. Spectrum's menu (`sp-menu-item-added-or-updated`), Lion's form system (`form-element-register`), Calcite's tabs.
5. **Context.** The root provides a value through `@lit/context`, and each part consumes it. This is the mechanism of candidate A. Carbon's newer components (tearsheet, card, page header, interstitial screen, coachmark, menu, grid, notification panel), PatternFly Elements (tabs, dropdown, table) and the Red Hat Design System (tabs, accordion, progress stepper and others).
6. **The parent renders everything, and the children carry data.** UI5 marks its part elements `@abstract`: `ui5-tab` and `ui5-wizard-step` hold properties and content, and the parent draws the tab strip or the wizard header from them in its own shadow DOM. Ionic's select builds its overlay from `ion-select-option` elements. This is the form nearest to candidate C. No surveyed library builds tabs, an accordion or a stepper as one element with no part elements. Vaadin's menu bar takes its items as data only.

### What happens to a part inside a wrapper element
- Under mechanism 1 the wrapped part is not found, because the wrapper is the assigned element or the direct child. This is read from the source for Web Awesome, Shoelace, Spectrum, Fluent UI, UI5, Lion and Vaadin. It is stated in writing in two places only: a source comment of Material Web's list ("will _only_ include direct children / directly slotted elements") and the Web Awesome accordion docs ("properties like `mode` apply only to direct children").
- Four code paths were written for wrappers. Material Web's list controller takes a wrapper that exposes the item in an `item` property. The button groups of Web Awesome and Shoelace search inside each assigned element; Shoelace's docs say "Buttons can be wrapped in tooltips". Spectrum's menu descends into every assigned element that is not an item. GitHub's tab container has a `tablist-wrapper` slot.
- Under mechanisms 2, 3, 4 and 5 the wrapped part works, as long as the wrapper is in the same tree. This is read from the source, not from documentation.
- Mechanism 2 also finds the parts of a nested instance of the same component. GitHub's tab container filters these out with `closest(...) === this`. The searches of Carbon and Ionic, and of the select and radio group of Web Awesome and Shoelace, have no such filter (read from the source).
- Context alone does not give any depth. In PatternFly Elements and the Red Hat Design System the context carries state down, but the parent lists its tabs and accordion headers from its direct children. A wrapped part gets the state and is still missing from the list.
- A shadow root between parent and part stops `querySelectorAll`, `closest` and events that are not composed. Lion stops its registration event at shadow roots on purpose, for accessible relationships in one tree.
- The docs of UI5, Ionic, Fluent UI, Lion, Vaadin, Calcite, PatternFly Elements, the Red Hat Design System and Carbon's older components were not read for a statement on wrappers. For these, whether the behaviour is documented is not known.

### A ready-made form beside a composed form
- Two elements offer both forms on the same element. Vaadin's select takes an `items` array, or a slotted `<vaadin-select-list-box>` with `<vaadin-select-item>` children; the two cannot be mixed, and the data form creates the same part elements. Spectrum's table takes composed head, body, row and cell elements, or `items` with a `renderItem` function.
- No component in the lists read has a full set of exported parts and a second exported element that composes those same parts. The lists of UI5, Vaadin and Material Web were not read in full.
- The libraries reach the ready-made case in another way. A part element is coarse: Web Awesome's `wa-step` is one element with three slots and nine CSS parts, where Chakra UI's Steps snippet composes eight part components for one step (Item, Trigger, Indicator, Status, Number, Title, Description, Separator; RES-042). A high-level element composes other exported elements inside its own shadow DOM: Material Web's select renders `<md-menu>`, Web Awesome's select renders `<wa-popup>`, Carbon's menu button renders `<cds-button>`.
- Carbon documents its new tearsheet as "Tearsheet (New Composable)". Its docs list eight elements, which share state through context. Directories named `tearsheet-deprecated` and `page-header-deprecated` stand beside the new versions. The form of the earlier tearsheet was not read; the earlier page header also has part elements, without context.

### 2. Parts at any depth below their root, and the use of context
- Carbon's newer components have the shape of the compound pattern of React libraries. The root holds a `ContextProvider` with `{ state, setState }`, each part consumes it with `subscribe: true`, and parts write back through `setState`.
- Material Web's experimental `labs/gb` menu also registers parts through context: the value holds `itemConnected(item)` and `itemDisconnected(item)`, and the menu sorts the registered items by document position. The labs folder is marked as not for production.
- Without context, parts work at any depth in Spectrum's menu and Lion's form system (registration event), in Ionic (the part calls `closest`), and in Media Chrome (bubbling request events, state attributes set on descendants, or an ID in the `mediacontroller` attribute for a control outside the root).
- Web Awesome's stepper drives Next and Back from any element on the page with `data-stepper="next <id>"`. It has no Next or Back part.
- Use of `@lit/context`: Carbon (state between a root and its parts), PatternFly Elements and the Red Hat Design System (state from a parent down to its parts), Web Awesome (only the depth of a tree item), Material Web (only the labs menu). FAST Element implements the Context Community Protocol itself. Spectrum has its own event protocol in `sp-theme`. Shoelace, Lion, Vaadin, UI5, Ionic, Fluent UI and Calcite do not use the protocol.
- The part that upgrades before its provider (prototype, case 2) is known in practice. PatternFly Elements and the Red Hat Design System create every context through a helper that attaches a `ContextRoot` to `document.body`. Carbon, Material Web and Web Awesome do not install one. A Lit maintainer names `ContextRoot` with subscribing consumers as the answer, attached "to the root of your app that's upgraded before anything else". The Lit issue on this is open, and a team member wrote in 2024 that the team considered applying context roots automatically.
- Zag.js, the state machine layer under Chakra UI, has no adapter for Lit or custom elements.

### 3. What the sources state as practice
- **lit.dev**: "properties down, events up". A component "should be the source of truth for the subcomponents in its shadow DOM". For light DOM children the component uses `<slot>` and `slotchange`, and it "can't assume a static set of child nodes". Context is named for "when data-binding isn't an option, such as when an element needs to provide data to its light DOM children". lit.dev shows both shapes without choosing: a menu with an `items` property whose items are in its shadow root, and a parent with light DOM children like `<select>` and `<option>`.
- **Lit maintainers** (GitHub replies; no talk or post was found): a parent sets state and uses `slotchange` to react to its children. Context "is not an object observation system, or really a reactivity system"; "It's a way to distribute values down the DOM tree." Context to light DOM children has a timing problem that `ContextRoot` addresses.
- **Google** (web.dev, 2017): children that the element creates go into its shadow root; light DOM children are projected with `<slot>`. The reference `<howto-tabs>` finds its parts with `querySelectorAll` and waits for `customElements.whenDefined`.
- **Gold Standard checklist** (archived 2022): a component should work "with any type of child elements", may treat certain types specially, should use duck typing, and must respond to content changes with `slotchange`. It should consider what it does "inside a plain parent element such as a `<div>`".
- **Web Components Community Group**: Context is the only protocol that concerns a parent and its descendants. It is a Candidate, not Accepted. No protocol covers how a parent lists or orders its parts.
- **Open UI**: it describes each component by its anatomy, parts and slots. Its customizable select changed the HTML parser so that `<option>` may sit inside "almost all tags" below `<select>`.
- None of these sources states which mechanism a parent with parts should use. None states what should happen to a part inside a wrapper element.

### 5. Where the practice differs from Chakra UI (RES-042)
1. **How state is shared.** Chakra's parts read a React context that the root fills from a state machine, so every part works at any depth. Most surveyed parents read their slot or their direct children. Context is used by Carbon, PatternFly Elements and the Red Hat Design System, and in the last two only for state that goes down.
2. **How fine the parts are.** Chakra's Steps has eighteen flat components, its providers and contexts included (RES-042). Web Awesome's stepper has two elements; the smaller pieces are slots and CSS parts of `wa-step`. Carbon's new tearsheet lists eight elements.
3. **Where the ready-made form lives.** Chakra's package has none; the CLI copies snippets into the consumer's project, and the consumer owns them. In the web component libraries the element itself is the ready-made form at a coarser grain, and two elements add a data property. No source read here describes snippets that are copied into a project.
4. **How a developer replaces a part's element.** Chakra has `asChild` and `as`. The web component libraries accept another element that carries a marker: an attribute (`md-list-item`, `md-tab` in Material Web), an ARIA role (`role="tab"` in Spectrum and GitHub), a property (`_hasVaadinItemMixin` in Vaadin) or a `slot` attribute on a plain element (Lion). No equivalent of merging a part onto a child element was found.
5. **How code outside the tree reads or drives state.** Chakra has `RootProvider`, `useSteps` and `Steps.Context`. The web component libraries use the element's own properties, methods and events, or an ID reference (`data-stepper`, `mediacontroller`).
6. **How style reaches a part.** Chakra passes per-part styles through a React context. The web component libraries use `::part`, CSS custom properties, and attributes that the parent copies to its parts (Carbon).
7. **Order of arrival.** A part element can upgrade before its parent. The libraries handle this with `customElements.whenDefined`, with `ContextRoot`, or by moving work to `firstUpdated`. RES-042 records no such step for Chakra.
8. **Export shape.** Chakra exports a namespace (`Steps.Root`). The web component libraries export tag names with a shared prefix (`wa-stepper`, `wa-step`).

### Limits and contrary evidence
- Wrapper behaviour was read from source code. It was not run in a browser, except for the three candidates of the prototype.
- UI5, Vaadin and Calcite were read at prerelease versions of their main branches. Shoelace's last commit is of 2026-05-14.
- Closed-source libraries (for example Salesforce Lightning, Shopify Polaris, Tailwind Plus Elements) were not read.
- UNVERIFIED: whether a talk or a blog post of a Lit maintainer states more than the GitHub replies. Three searches found none.
- Against "reading the slot is the practice": Carbon and Ionic take parts at any depth, and three libraries use context in production.
- Against "context gives parts at any depth": PatternFly Elements and the Red Hat Design System still list parts from direct children.
- RES-043 found no source that makes slots see through a wrapper. The platform still has none. The four code paths above are library code that walks into the wrapper.
- RES-043 marked manual slot assignment with Lit as undocumented. GitHub's tab container uses `slotAssignment: 'manual'` in production, without Lit.

### Web Awesome 3.14.0 (Lit 3; commit 1828b3992c6f)
Paths are below https://github.com/shoelace-style/webawesome/blob/1828b3992c6fee46182150422fdf4945e6521012/packages/webawesome/.
- `@awesome.me/webawesome` is version 3.14.0 and depends on `lit ^3.2.1` and `@lit/context ^1.1.6`. Source: package.json, checked 2026-11-13.
- `wa-tab-group` finds its tabs with `slot[name="nav"].assignedElements()` filtered to `wa-tab`, and its panels with `defaultSlot.assignedElements()` filtered to `wa-tab-panel`. Neither call uses `flatten`. It re-syncs on `slotchange` and on a subtree `MutationObserver` that ignores mutations whose target has another closest `wa-tab-group`. A `wa-tab` inside a wrapper element is therefore not in the list (read from the source; the docs page does not state it). Source: src/components/tab-group/tab-group.ts:98-121, 168-180, 448, 472, checked 2026-11-13.
- `wa-stepper` (new in 3.14) finds its steps with `defaultSlot.assignedElements().filter(el => el.localName === 'wa-step')`. A comment gives the reason: "Scoped to this stepper's own light-DOM children via slot assignment, so a stepper nested inside a step's description ... doesn't get pulled into this one's step list." The parent sets position, active and locked state on each step. A step inside a wrapper element is not found (read from the source). Source: src/components/stepper/stepper.ts:171-176, 326, checked 2026-11-13.
- `wa-stepper` has no Next or Back part. Any element on the page with `data-stepper="next <id>"`, `"previous <id>"` or `"goto <id> <name>"` drives the stepper with that ID. One click listener on `document` resolves the ID in the invoker's root node. The comment calls these "invokers" and names the same convention for `data-dialog` and `data-drawer`. Source: src/components/stepper/stepper.ts:337-366, checked 2026-11-13.
- `wa-accordion` finds its items with `defaultSlot.assignedElements({ flatten: true })` filtered to `wa-accordion-item`, and checks ownership of an event's item with `item.closest('wa-accordion') === this`. The docs say that with nested accordions "properties like `mode` apply only to direct children". Source: src/components/accordion/accordion.ts:51-63 and docs/docs/components/accordion.md:328, checked 2026-11-13.
- Other parents of Web Awesome search all descendants in the light DOM, not the slot: `wa-select` uses `this.querySelectorAll('wa-option')`, `wa-radio-group` uses `this.querySelectorAll('wa-radio')`, `wa-checkbox-group` uses `this.querySelectorAll(':is(wa-checkbox, wa-switch)')`, and `wa-tree` uses `this.querySelectorAll('wa-tree-item')`. A part inside a wrapper element is found by these (read from the source). `wa-dropdown` uses `defaultSlot.assignedElements({ flatten: true })`. Source: src/components/select/select.ts:692-697, radio-group/radio-group.ts:205-206, checkbox-group/checkbox-group.ts:92, tree/tree.ts:237-238, dropdown/dropdown.ts:156-157, checked 2026-11-13.
- `wa-button-group` allows a wrapper on purpose: `findButton` returns `el.closest(selector) ?? el.querySelector(selector)`, with the comment "The button could be the target element or a child of it (e.g. a dropdown or tooltip anchor)". Source: src/components/button-group/button-group.ts:83-87, checked 2026-11-13.
- The only use of `@lit/context` in Web Awesome is `wa-tree-item`: each item provides `{ depth, expanded }` and consumes the same context from its parent item (`subscribe: false`), to know its depth. The tree itself still finds its items with `querySelectorAll`. Source: src/components/tree-item/tree-item.ts:1, 23-24, 104-108, 132-133, checked 2026-11-13.
- No component of Web Awesome with parts takes its parts as data. The component list holds each parent beside its part element (`accordion` and `accordion-item`, `stepper` and `step`, `tab-group`, `tab` and `tab-panel`, `select` and `option`, `dropdown` and `dropdown-item`, `tree` and `tree-item`, `carousel` and `carousel-item`, `breadcrumb` and `breadcrumb-item`, `toast` and `toast-item`). Source: directory listing of src/components, checked 2026-11-13.

### Spectrum Web Components 1.12.6 (first generation, Lit 2 or 3; commit a6d0b064454c)

- In the component lists read for this record (Web Awesome, Shoelace, Carbon, Ionic, Fluent UI, Lion, Spectrum, Calcite), no component has both a full set of exported part elements and a second exported element that composes those same parts. The lists of UI5, Vaadin and Material Web were not read in full. Source: the directory listings of the commits named above, checked 2026-11-13.

### Stated practice: lit.dev and the Lit maintainers
- lit.dev names the topic "component composition": "building a large, complex component out of smaller, simpler components". Its rule is "properties down, events up". It shows two shapes. In the first, a `my-menu` "includes a set of menu items and exposes `items` and `selectedItem` properties as part of its public API", and the `my-item` elements are in the menu's shadow root. In the second, the parts are "light DOM children", "like the standard `<select>` element can take a set of `<option>` elements as children"; the component places them with `<slot>` and learns of changes from `slotchange`. Source: https://lit.dev/docs/composition/component-composition/, checked 2026-11-13.
- The lit.dev content (docs for Lit 3, articles and blog at commit 697feba856f5 of 2026-04-30) does not contain the words "compound" or "composite". It uses "subcomponent" (11 times in 4 files), "light DOM children" (8 times), "slotted children" (6 times) and "child element" or "child component" (7 times). Source: a text search of https://github.com/lit/lit.dev/tree/697feba856f5fc9284a7f5e2df52a6a690260aab/packages/lit-dev-content/site (docs/v3, articles, blog), checked 2026-11-13.
- A Lit maintainer, on a parent that wants to update its slotted children: "In general you should not need to call requestUpdate() on another component. You should set some state that the component responds to. If you want to respond to children changing, you can use the slotchange event". Source: https://github.com/lit/lit/discussions/3798 (reply of justinfagnani, marked Maintainer, 2023-04-11), checked 2026-11-13.
- A Lit maintainer, on the scope of context: "WCCG context is not an object observation system, or really a reactivity system It's a way to distribute values down the DOM tree. If those values are mutated you need to find a way to subscribe and notify". Source: https://github.com/lit/lit/discussions/5129 (reply of justinfagnani, marked Maintainer, 2025-10-24), checked 2026-11-13.
- A Lit maintainer, on context from a parent to its light DOM children: "This normally isn't an issue for elements that provide to either their shadow DOM children, because they are always created after the provider. But it can be an issue when providing to light-DOM children. Either in this slotted case, or without slots if the child is upgraded before the parent". The stated answer is `ContextRoot`, with consumers that subscribe. In the same issue on 2026-03-21: "You need to attach the ContextRoot to the root of your app that's upgraded before anything else. You can attach it to document.body too." A team member wrote on 2024-04-12 that the team is "considering making context roots be auto applied to the document/window rather than manual". The issue is open in the page read. Source: https://github.com/lit/lit/issues/4618 (replies of justinfagnani, marked Collaborator, 2024-04-11 and 2026-03-21; reply of augustjk, marked Member, 2024-04-12), checked 2026-11-13.
- The README of `@lit/context` has a section "Late upgraded Context Providers": "LightDOM content below this provider may end up requesting a context that is currently not provided by any provider. To solve this case we provide a `ContextRoot` class". It names the cost: "a small overhead, in that if a provider is not within the DOM hierarchy of the unsatisfied requests we are unnecessarily refiring these requests". Source: https://raw.githubusercontent.com/lit/lit/main/packages/context/README.md (lines 176-196), checked 2026-11-13.

### Stated practice: Google, the Gold Standard, the Community Group and Open UI
- Google's "Custom Element best practices" (last updated 2017-08-14) has two items on children: "Place any children the element creates into its shadow root", because they "are part of its implementation and should be private", and "Use <slot> to project light DOM children into your shadow DOM", because it "makes your component more composable". Both name `<howto-tabs>` as the example. The checklist has no item on how a parent finds its child elements or on wrapper elements. Source: https://web.dev/articles/custom-elements-best-practices, checked 2026-11-13.
- Google's reference element `<howto-tabs>` puts `howto-tab` and `howto-panel` children into two named slots, listens for `slotchange`, waits for `customElements.whenDefined` of both parts, and then finds its parts with `this.querySelectorAll('howto-tab')`. It pairs a tab with its panel by `tab.nextElementSibling`. Its comment: "All children of `<howto-tabs>` should be either `<howto-tab>` or `<howto-tabpanel>`". Source: https://github.com/GoogleChromeLabs/howto-components/blob/master/elements/howto-tabs/howto-tabs.js (lines 52-58, 66-83, 106-114, 144-150, 178-187), checked 2026-11-13.
- The Gold Standard checklist for web components (archived on 2022-07-26, last edited 2020-09-29) has four items on a parent and its children: "Content Assignment", "Content Changes", "Parent/Child Independence" and "Auxiliary Content". "Parent/Child Independence" says: "Unless there is a direct need, it's usually best to design a component such that it can work inside any type of parent element and ... with any type of child element", "It's fine for a component to treat certain types of children specially (e.g., a `<select>` treats `<optgroup>` children differently than `<option>` children)", "Consider what the component should do if found inside a plain parent element such as a `<div>`", and "consider using duck typing to see whether the parent/child supports the interface members you require". "Content Changes" requires the processing of children at first render and "Whenever the component content (including distributed content) changes", with `slotchange`. "Content Assignment" asks that content passed through another component's `<slot>` be treated "as if it were directly inside the component". Source: https://github.com/webcomponents/gold-standard/wiki and its pages Parent-Child-Independence, Content-Changes and Content-Assignment, checked 2026-11-13.
- The Web Components Community Group lists four protocols: Context (Candidate), Defer Hydration (Proposal), Pending Task (Draft) and Slottable Request (Proposal). None is "Accepted"; "To move to 'Accepted' a proposal needs 2 implementations." No listed protocol defines how a parent lists or orders its child elements. Source: https://github.com/webcomponents-cg/community-protocols (README, last commit 2026-04-24), checked 2026-11-13.
- Open UI names the structure of a component its "Anatomy: The parts that make up the control/component". Its spec template has "Anatomy" with a "Slots" table under the question "What parts of the component are composable or replaceable?". Its glossary defines "Composite Component: It is often necessary to produce a component that contains other components ... These types of components are commonly referred to as composite components." The words "compound component" and "subcomponent" do not occur in the Open UI pages; "compound control" occurs in the focusgroup explainer. Source: https://github.com/openui/open-ui/blob/8ec06c9126e6d4aecdfa19af6f6c440d15be048f/site/src/pages/glossary.mdx (lines 13-21), component-spec-template.mdx (lines 87-105), and a text search of site/src/pages, checked 2026-11-13.
- Open UI's customizable select changed HTML so that a part may sit inside wrapper elements: "The old behavior in the HTML parser for `<select>` is to remove all tags which aren't `<option>` or `<optgroup>`. We changed the HTML parser to allow almost all tags as descendants of `<select>`". Source: https://github.com/openui/open-ui/blob/8ec06c9126e6d4aecdfa19af6f6c440d15be048f/site/src/pages/components/customizable-select.explainer.mdx (lines 58-60), checked 2026-11-13.
- Three web searches for a talk or a post of a Lit maintainer on a parent and its child elements found one abstract only: a 2019 talk by a Lit maintainer that lists "cross-component coordination" and "context-like APIs based on events" among its topics. No transcript was read. Source: https://devfest2019.gdgnantes.com/sessions/building_a_complex_application_with_web_components_and_litelement/ (search result excerpt), checked 2026-11-13.
- Of the libraries that use `@lit/context`, only PatternFly Elements and the Red Hat Design System install a `ContextRoot`. The source trees of Carbon Web Components, Material Web and Web Awesome do not contain the name `ContextRoot`. Source: a text search of the three repositories at the commits named above, checked 2026-11-13.
- Carbon's older parents copy an attribute to their parts for styling, with the comment: "Propagate `size` attribute to descendants until `:host-context()` gets supported in all major browsers". Source: https://github.com/carbon-design-system/carbon/blob/7b78335fe724fa772b113bf5395882cb9fc9dd98/packages/web-components/src/components/accordion/accordion.ts (lines 56-66), checked 2026-11-13.
- A spike comment in the Carbon for IBM Products repository uses the React name for the web component case: "Does this model support a compound component pattern? Yes. Compound components map well to Web Components using nested custom elements and slots ... The React wrapper can re-expose them using namespace patterns like Select.Option or Select.Trigger. Systems like Spectrum SWC and UI5 already follow this model". Source: https://github.com/carbon-design-system/ibm-products/issues/8900 (issue opened 2026-01-30), checked 2026-11-13.
