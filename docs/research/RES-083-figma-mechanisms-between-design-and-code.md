# RES-083: What Figma provides to connect code with what is built in Figma

## Question
Which mechanisms do Figma and the tools around it provide to connect code with what is built in Figma: what can each read from a Figma file, what can each write, does it run with no person, which plan does it need, and how robust is it?

Peter asked for this research on 2026-11-20, with `/deep-research`, in his reply to IDEA-011#02. His words: "I'd like you to research what is provided by figma, how other large/popular design-systems handle this exact type of thing - you should fan out and cover a lot of ground here."

Needed by: IDEA-011#02, the source of truth of a block. The facts also bear on IDEA-002 rows 07, 10 and 11 and on IDEA-009#03. Earlier records hold parts of this: RES-023 to RES-028, RES-046, RES-049 and RES-075.

## Answer
Answered on 2026-11-20. The survey has 27 records, each for one mechanism or one group of tools: 22 that the main session named and 5 that a critic added. A second agent checked each record against the sources and corrected each.

The short answer for a team on Figma's Professional plan, which is Peter's plan:
- What reads a design system out of Figma: the Figma MCP server, the REST endpoints for files and nodes, the Plugin API, Dev Mode, and the native export of variables. The REST file endpoints return the whole tree of a file as data, with the properties of each component, the variables that are bound, the descriptions and the documentation links, and they run with no person.
- What writes into Figma: the Plugin API, and the MCP server through `use_figma`, which is in beta and will become a paid feature by use. No REST endpoint creates a component, a variant or a component property.
- What links a Figma component to its code: Code Connect. It maps the properties of a component, its nested instances and its slots to a code snippet, and Dev Mode and the MCP server show that snippet. On Professional it allows one library and one framework.
- What the Professional plan does not have: the Variables REST API and library analytics (Enterprise), plan access tokens for CI (Organization and Enterprise), branching and "Check designs" (Organization and higher), and extended collections (Enterprise).
- The MCP server on Professional reads at most 200 calls a day and 10 a minute for a Full or Dev seat. Figma's documentation does not say whether it can run with no person after the first sign-in.
- Figma components have slots, on every plan, beside variants, component properties and nested instances. The Plugin API and Code Connect know slots. It is not confirmed that the MCP server or the REST API read them.

What no mechanism carries, by the records:
- The behaviour of a component: events, keyboard handling and logic. Only prototype interactions are named.
- States, in the direction from Figma to code. One tool simulates hover, active and focus states, from code to Figma.
- Structure through the quick routes: a captured page and `html_to_figma` give flat layers, and Figma Make does not copy the structure of a library component.
- Annotations and descriptions through most routes: the REST specification has an empty type for annotations.

For Peter's reasoning of 2026-11-20, that a system built correctly in Figma can be read through the Figma MCP: the records support that the structure, the properties, the variables and the Code Connect snippets can be read. They do not support that behaviour and states come across; those are text in the design spec. RES-028 found two more limits in a live read: `get_design_context` changes bold and italic marks and drops pinned properties.

### Facts across the records
This part is the text of the last agent of the run, which states the facts across all records.

Scope. There are 26 records, all checked against sources up to 2026-11-20. Each record covers one mechanism or one group of tools. Every record has the verdict "corrected". This text uses only what the records say.

1. From Figma to code (direction "figma-to-code")
Mechanisms in this group:
- Figma REST API: files, nodes and images.
- Figma REST API: components, component sets, styles and published libraries.
- Figma Dev Mode.
- Documentation platforms: zeroheight, Supernova and Knapsack.
- Figma for VS Code.
- Visual comparison of a Figma design with rendered code.
- The @figma-export CLI.

What they carry:
- REST files and nodes reads the whole document tree as JSON. This includes componentPropertyDefinitions, instance componentProperties, boundVariables, descriptions and documentationLinks.
- The REST component, component-set and style endpoints return metadata of published assets only. They do not return property definitions, the layer tree or style values.
- Dev Mode shows layout, colour, typography, text, component properties, styles, variables with their modes and alias chains, and prototype interactions. It produces snippets that a person copies. Variable code syntax works only for CSS, SwiftUI and Compose.
- Figma for VS Code shows frames, code snippets with "modes and styles", component properties and Dev resources. It writes comments and Dev resources.
- zeroheight, Supernova and Knapsack read variables and components into documentation. zeroheight and Supernova can open pull requests with token files. None of the three writes into Figma. zeroheight says its sync is "one way".
- The visual comparison tools read rendered pixels and little node metadata. Examples are GET /v1/images, uiMatch and Applitools Figma Dev Comparison. They write images, diff reports and pass or fail results.
- @figma-export reads through three REST GET endpoints. It writes SVG files, React components, sprites, and CSS, Sass, Less or Style Dictionary files. Its source shows no support for variables.

What they cannot carry: none of these mechanisms writes design content into Figma. The REST file endpoints duplicate whole files only, and only on Enterprise.

2. From code to Figma (direction "code-to-figma")
Mechanisms in this group:
- Storybook integrations with Figma.
- Code-to-Figma generators: story.to.design, html.to.design and code.to.design.

What they carry:
- story.to.design builds native Figma components and variants from rendered stories. The output has auto layout, nested components, simulated hover, active, focus and tap states, and component properties.
- It turns CSS custom properties into Figma variables in one collection, with aliases and modes, and binds them to the layers.

What they cannot carry:
- They read little from the Figma file. story.to.design matches only colour and text styles, and it does not match Tokens Studio tokens.
- A generated component that a person edits loses its link to the code.
- The Storybook Designs addon and Storybook Connect only display or link. The Storybook record classifies itself as code-to-figma, but it states this breakdown.

3. Both directions (direction "both")
Mechanisms in this group:
- The Figma MCP server.
- The Figma REST API variables endpoints.
- The Figma Plugin API.
- Figma variables with their native import and export.
- Figma Make.
- Figma features that turn code into designs or designs into code (code layers, capture, Extract designs).
- Token tools: Tokens Studio, Style Dictionary, Terrazzo, Supernova, Specify and Knapsack.
- Design-to-code generators: Anima, Locofy and Builder.io.
- The group record on Figma releases of 2025 and 2026.

What they carry:
- MCP server, reading: design context and code, the metadata outline, the variables and styles used in a selection, screenshots and assets. Writing (use_figma, in beta): through Plugin API code it creates and changes pages, frames, components, variants, variables, styles and text.
- Variables REST API: reads and writes variables, collections, modes, values, aliases, scopes and codeSyntax. It reads and writes nothing else.
- Plugin API: reads and writes the node tree, component properties including SLOT, variables and modes, styles, text, layout and annotations.
- Native variables import: creates a collection from DTCG JSON files, one mode for each file. Native export writes the modes to JSON.
- Figma Make: reads library variables only as a subset, written into CSS with raw values. It writes app code and pull requests.
- Code layers and capture bring code onto the canvas as flat layers, with "No component and styles mapping yet".
- Of the six token tools, only Tokens Studio writes into Figma. It writes variables and styles.
- Anima and Builder carry a design back into Figma only through a person who pastes layers.

What they cannot carry:
- MCP html_to_figma and code to canvas give plain layers, not library components.
- Native import does not take composite DTCG tokens.
- Make does not yet replicate component structures from Figma libraries.

4. Link or metadata only (direction "link-or-metadata-only")
Mechanisms in this group:
- REST dev resources and comments.
- Figma webhooks.
- Figma Code Connect.
- The Figma component features for anatomy.
- Figma libraries, branching, version history and library analytics.
- Figma Check designs.
- Zeplin Connected Components.
- Figma Embed Kit 2.0 and the Embed API.
- The @figma/rest-api-spec package.

What they carry:
- A dev resource is a name and a URL on a node. It has "no typed mapping to code, props or variants".
- Webhooks send event notices with no design content.
- Code Connect maps component properties (string, boolean, variant, instance swap and slot) and nested instances to code snippets that Dev Mode shows. It writes connection data, not layers.
- Check designs binds hard-coded values to variables or styles inside Figma. For components it only flags issues. It does not compare Figma with code.
- Zeplin keeps a code summary and links for each component.
- The Embed API sends prototype navigation and state commands.
- The OpenAPI spec types the REST API. In the spec, AnnotationsTrait is an empty object.

5. Runs with no person (automation "runs-unattended")
- The REST file, node and image endpoints.
- The REST variables endpoints.
- The REST component, style and library endpoints.
- The REST dev resources and comments endpoints.
- Webhooks. Some events still depend on a person's action in Figma.
- @figma/rest-api-spec.
- @figma-export.

6. Mixed: a part runs with no person, a part needs one
- Plugin API: "It's not possible to build plugins that run in the background".
- Code Connect: publishing runs in CI.
- Dev Mode.
- Native variables import and export. The REST variables API is the CI path.
- The component features.
- Libraries.
- Token tools: Style Dictionary and Terrazzo builds and tz import run in CI.
- Documentation platforms: variables need a plugin sync started by a person.
- Design-to-code generators: the Anima SDK runs on a backend.
- Visual comparison: uiMatch runs in CI.
- The record on recent releases.
- Zeplin: its CLI runs in CI.

7. Needs a person or an open app
- Figma Make.
- Code layers and capture.
- Check designs.
- The Storybook integrations.
- The code-to-Figma generators.
- Figma for VS Code.
- Embed Kit.

8. Not confirmed
- The MCP server. Figma's docs say neither yes nor no about unattended runs after the first OAuth sign-in.

9. Plans and access
- MCP server: all plans. Reads are limited by seat:
  - View and Collab seats: up to 20 calls a month.
  - Full and Dev seats on Professional: 200 a day and 10 a minute.
  - Full and Dev seats on Organization: 200 a day and 15 a minute.
  - Full and Dev seats on Enterprise: 600 a day and 20 a minute.
  - Write to canvas will become a "usage-based paid feature".
- REST endpoints: need a personal access token (90 days at most), OAuth, or a plan access token.
  - Plan access tokens exist only for Organization and Enterprise. They have been generally available since 2026-07-23.
  - GET file, GET file nodes and GET image are Tier 1 endpoints.
- Variables REST API and the Library Analytics API: Enterprise only.
- Webhooks: file webhooks are limited to 150 on Professional, 300 on Organization and 600 on Enterprise.
- Plugin API: all plans, by seat. Private plugins need Organization or Enterprise.
- Code Connect: a Dev or Full seat on Professional, Organization or Enterprise. Professional allows one active library and one active framework.
- Dev Mode: not on Starter. It needs a Full or Dev seat. Prices:
  - Professional: Full $16, Dev $12, Collab $3.
  - Organization: Full $55, Dev $25, Collab $5.
  - Enterprise: Full $90, Dev $35, Collab $5.
- Figma for VS Code: Professional, Education, Organization and Enterprise, with a Full or Dev seat.
- Variables: all plans.
  - Modes per collection: 10 on Professional, 20 on Organization. Enterprise has "Unlimited modes with extended collections".
  - Extended collections: Education (K-12), Government and Enterprise.
- Component properties and slots: all plans, with edit access to the file.
- Library publishing: Professional and higher. Starter cannot publish.
- Branching: Education (K-12), Organization, Government and Enterprise.
- Check designs: Education (K-12), Organization, Government and Enterprise.
- Code layers: Starter, Professional, Education (not K-12), Organization and Enterprise. They use AI credits: 500 a Full seat on Starter, 3,000 on Professional, 3,500 on Organization and 4,250 on Enterprise.
- Figma Make: Starter and the paid plans. The records disagree on which plans get Make kits.
- Third-party tools have their own prices:
  - Tokens Studio: Free; Team €39 a month; Organization €499 a month.
  - Terrazzo: free. It can import variables only from Enterprise.
  - story.to.design: Team $149 or $199 a month.
  - html.to.design PRO: $18 a user a month, or $12 billed yearly.
  - Zeplin: Free is $0.
  - Anima, Builder and Locofy: their own plans. Builder's index-repo command needs its Enterprise plan.
  - The Storybook Designs addon, @figma-export and rest-api-spec are free (MIT).
  - Storybook Connect needs Chromatic.
