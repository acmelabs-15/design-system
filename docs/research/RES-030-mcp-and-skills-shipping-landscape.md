# RES-030: How libraries ship MCP servers and agent skills, and how agent hosts find them

<!-- Add outcome: answered, partial or blocked to frontmatter when an answer or a block is known. Only answered work can become resolved. -->

## Question
How do other libraries ship MCP servers and agent skills (inside the library package or apart), how do they install them into a consumer project, and how do agent hosts find them?

## Answer
Partly answered. The sweep of 2026-11-12 established where Ant Design, shadcn/ui, Chakra UI, MUI, Nuxt UI, Storybook and TanStack Intent ship their MCP servers and skills, how each installs them, which host files the installs write, how each keeps versions in step, and what the Agent Skills format requires. The sufficient-answer condition is not met; see "Still open".

Question 1 of the former "Next action" is answered: a single research agent read the six hosts' own documentation on 2026-11-12 (Findings, "Agent hosts, from their own documentation"). Question 2 is still open.

- node_modules: no host's documentation names `node_modules` as a place where it finds skills or MCP server definitions. A package's skills reach a host only through a host folder (a copy, or a symlink where the host documents symlinks: Claude Code and Codex), a plugin, or a VS Code extension. The Agent Skills client guide tells clients to skip `node_modules/`. Claude Code and Codex plugin marketplaces can fetch a plugin from an npm package, which they copy into their own plugin cache.
- `.agents/skills/` is read by Codex, Cursor, Gemini CLI and Devin, and by VS Code's Codex harness. Claude Code's skills page does not name it.
- Refresh after a change: Claude Code, Codex, Cursor (skills at start) and Gemini CLI (`/skills reload`) pick up skill changes; Cursor needs a restart for changed MCP servers; Gemini CLI has `/mcp reload`; VS Code starts trusted workspace servers again after a change without a prompt. What Codex and Devin do after an edit to an MCP config file is not documented in the pages read.

Disagreements and corrections:

- The earlier library-side finding gives VS Code `.vscode/mcp.json` with `servers`. VS Code's own docs (DateApproved 11/11/2026) call that the deprecated Local format and name workspace-root `.mcp.json` and `~/.copilot/mcp-config.json` with `mcpServers` for Copilot.
- The earlier finding gives Windsurf `~/.codeium/windsurf/mcp_config.json`. Windsurf's docs now redirect to Devin Desktop, which uses `.devin/mcp_config.json` and `~/.config/devin/mcp_config.json` and only imports the Codeium file.
- Skill precedence: the Agent Skills guide says project skills override user skills, and Gemini CLI agrees (workspace highest). Claude Code says "personal over project".
- Codex's project `.codex/config.toml`, which shadcn's docs say the CLI cannot write and a third-party guide said exists, is confirmed by Codex's own docs, for trusted projects only.

Not documented in the pages read: the edit date of the Claude Code, Codex, Cursor and Devin pages; a separate approval of a project's `.cursor/mcp.json` server in Cursor; npm as a plugin source in Cursor, VS Code, Gemini CLI or Devin; a marketplace for Devin agent plugins. This run did not read modelcontextprotocol.io; each host's own pages define its configuration files.

### What the run established
The summary of the run's report, in its own words:

> As of November 2026, the libraries checked ship MCP servers and agent skills in four ways. 1. A separate npm package run through npx: MUI uses @mui/mcp, Chakra UI uses @chakra-ui/react-mcp and Ant Design uses @ant-design/cli. 2. A subcommand of the library's existing CLI: shadcn runs `shadcn mcp`. 3. A hosted HTTP server: Nuxt UI runs one at ui.nuxt.com/mcp, and Chromatic can host a published Storybook MCP. 4. A dev-server addon released together with the library: Storybook's @storybook/addon-mcp. Agent skills come either from GitHub through the third-party skills CLI (Nuxt UI and Chakra UI) or inside the library's own npm package (the TanStack Intent model). Installation ranges from fully manual edits to each agent host's config (MUI, Chakra UI and Nuxt UI) to an init or setup command that writes project files for named clients: `shadcn mcp init --client ...` and `antd setup --client claude|cursor|vscode|codex --mode mcp|skill|both`. Storybook uses the third-party mcp-add CLI. The config files named are .mcp.json (Claude Code), .cursor/mcp.json, .vscode/mcp.json (under a `servers` key), ~/.codex/config.toml (user level, which shadcn's CLI cannot write), ~/.gemini/settings.json, Windsurf's mcp_config.json and ~/.copilot/mcp-config.json. Version alignment also varies. MUI's documented config floats on @latest, and Nuxt UI's hosted server is not tied to any installed version. TanStack Intent skills live in node_modules, so they are pinned to the installed version and change with npm update. From 10.6, Storybook releases its MCP packages with Storybook itself, uses caret peer dependencies, and serves version-matched skills from the installed Storybook through `storybook skills get`.

### The question sent to the workflow
> As of November 2026, how do UI component libraries and developer tools ship MCP (Model Context Protocol) servers and agent skills for coding agents? (1) Where do they ship them: inside the library's own npm package, as separate packages, or as hosted servers? Name concrete projects and what each does, for example shadcn/ui, Chakra UI, MUI, Ant Design, Mantine, Storybook, Astro, Tailwind CSS, TanStack (including TanStack Intent), Nuxt UI, Vercel and Figma. (2) How do they install the server and the skills into a consumer project: an init command or a package.json bin script, and which files it writes, such as .mcp.json, AGENTS.md, CLAUDE.md, .claude/skills or .cursor/rules? (3) How do agent hosts find MCP servers and skills: Claude Code, Codex, Cursor, VS Code Copilot, Gemini CLI and Windsurf, including configuration files, plugins and marketplaces, and the Agent Skills format? (4) How do they keep the server and the skills in step with the installed version of the library, and how does an update reach a consumer project? Context: a design system plans to ship its MCP server and its agent skills inside its npm package, with an init script. Prefer primary sources: official documentation, source repositories and release notes, with their dates. Report facts and the disagreements between sources. Give no recommendation and no opinion.

## Findings
- Ant Design's official MCP server is not in the antd component package. It ships in the separate @ant-design/cli package (v6.3.5 or later) and starts with `antd mcp` (or `npx -y @ant-design/cli mcp`), which provides 8 tools and 2 prompts. The same CLI has `antd setup --client &lt;claude|cursor|vscode|codex>`, which writes project configuration in three modes (mcp, skill or both) and takes --dry-run, --check and --write-instructions flags. Evidence: Two claims merged, both voted 3-0. The quote: 'Starting from @ant-design/cli v6.3.5, you can launch an official MCP server with the antd mcp command, providing 8 tools and 2 prompts.' The npm registry shows that antd defines no bin, while @ant-design/cli defines bin { antd: 'dist/index.js' } (v6.7.0, 2026-11-04). The docs show the setup examples and list the supported clients and modes. They do not say which files setup writes or what --check and --write-instructions do. A server-side --version argument pins the antd version the docs data comes from. Confidence high; vote 3-0, 3-0. Source: https://ant.design/docs/react/mcp/, checked 2026-11-12.
- shadcn/ui's MCP server is the `mcp` subcommand of the shadcn CLI package (`npx shadcn@latest mcp`). It is not a separately named package. It browses, searches and installs items from shadcn-compatible registries configured in the consumer's components.json. `npx shadcn@latest mcp init --client claude|cursor|vscode|codex|opencode` runs in the project, and the docs place the config in .mcp.json for Claude Code, .cursor/mcp.json for Cursor and .vscode/mcp.json for VS Code with Copilot. For Codex the CLI cannot write ~/.codex/config.toml. It installs the dependency and prints manual steps. Evidence: Three claims merged, each voted 3-0. Docs quote: 'The MCP server acts as a bridge between your AI assistant, component registries and the shadcn CLI.' Docs quote on Codex: 'The shadcn CLI cannot automatically update ~/.codex/config.toml.' In the CLI source, the codex branch installs shadcn, prints instructions and exits without calling runMcpInit, even though the CLIENTS table lists configPath .codex/config.toml. npm shows shadcn 4.23.0 with the single bin `shadcn`. A third-party guide (shadcn.io) says Codex also reads a project-level .codex/config.toml in trusted projects. The official shadcn docs do not say this. Confidence high; vote 3-0, 3-0, 3-0. Source: https://ui.shadcn.com/docs/mcp and https://github.com/shadcn-ui/ui (packages/shadcn/src/commands/mcp.ts; apps/v4/content/docs/(root)/mcp.mdx), checked 2026-11-12.
- Chakra UI ships its MCP server as the separate npm package @chakra-ui/react-mcp. The server supports only stdio. Installation is manual, one host at a time: a server block that runs `npx -y @chakra-ui/react-mcp` goes in .vscode/mcp.json (servers key), .cursor/mcp.json, ~/.codeium/windsurf/mcp_config.json or a custom client (mcpServers key), or Zed settings.json (context_servers). For Claude Code the user runs `claude mcp add`. Chakra documents no init or bin script. Skills are installed separately from GitHub with the third-party `npx skills add` CLI. Evidence: Two claims merged, both voted 3-0. The quote: 'The MCP server currently supports only stdio transport and is published at @chakra-ui/react-mcp.' The latest npm version is 2.1.1, published about a year ago, with 9 versions. The two sources disagree on tool names. The docs list list_components and list_component_templates. The npm README lists get_components and list_blocks. Confidence high; vote 3-0, 3-0. Source: https://chakra-ui.com/docs/get-started/ai/mcp-server and https://chakra-ui.com/docs/get-started/ai/skills and https://www.npmjs.com/package/@chakra-ui/react-mcp, checked 2026-11-12.
- MUI ships its MCP server as the separate package @mui/mcp. It runs locally over stdio. Every documented config uses `npx -y @mui/mcp@latest`, so the server version follows the latest npm publish and not the @mui/material version installed in the project. MUI provides no init or bin script. Users add the server through each host's own UI or CLI. For Claude Code that is `claude mcp add`, which uses local scope by default and user scope with -s user; the README says this writes ~/.claude.json and never the repository's shared .mcp.json. Guidance files (.github/instructions/mui.md and a CLAUDE.md block) are created by hand. Evidence: Three claims merged, each voted 3-0. The quote: 'The MCP is available as a separate package that runs locally and communicates via your AI client using the stdio transport.' The README arrived with mui-x commit 1cf504e, '[mcp] Add @mui/mcp server and @mui/x-agent-tools (#22947)', dated 2026-07-06. VS Code also needs the chat.mcp.enabled and chat.mcp.discovery.enabled settings. Zed can install the server as an extension. That the server is absent from @mui/material is an inference: the docs do not state it. Confidence high; vote 3-0, 3-0, 3-0. Source: https://mui.com/material-ui/getting-started/mcp/ and https://github.com/mui/mui-x/blob/master/packages/mcp/README.md, checked 2026-11-12.
- Nuxt UI hosts its MCP server at https://ui.nuxt.com/mcp over HTTP. It is not a local process from the @nuxt/ui package. Installation is manual, with one snippet per host: `claude mcp add --transport http` for Claude Code; .cursor/mcp.json or a deeplink for Cursor; ~/.gemini/settings.json (httpUrl) for Gemini CLI; .vscode/mcp.json (servers key) for VS Code; .codeium/windsurf/mcp_config.json (serverUrl) for Windsurf; and /mcp add or ~/.copilot/mcp-config.json for Copilot CLI. Its agent skill lives on GitHub at skills/nuxt-ui/SKILL.md on the v4 branch. It is installed with the third-party skills CLI (`npx skills add nuxt/ui`, which supports 35+ agents and takes --agent, --global or the website URL), with `claude skill add &lt;github url>`, or with a Cursor deeplink. It is not shipped in the npm package. Evidence: Four claims merged, each voted 3-0. The quote: 'The Nuxt UI MCP server uses HTTP transport ... MCP server URL: https://ui.nuxt.com/mcp.' The server is built with @nuxtjs/mcp-toolkit, which serves /mcp on the deployed docs site. A verifier ran `npm pack @nuxt/ui` on 4.12.0 (2026-10-15): the package has no bin and no skill, AGENTS or mcp files. The docs call the skills CLI 'the easiest way', which is not the same as calling it recommended. Claude Desktop reaches the server through a local `npx mcp-remote` proxy. Confidence high; vote 3-0, 3-0, 3-0, 3-0. Source: https://ui.nuxt.com/docs/getting-started/ai/mcp and https://ui.nuxt.com/docs/getting-started/ai/skills and https://nuxt.com/blog (Building an MCP Server for Nuxt), checked 2026-11-12.
- TanStack Intent (@tanstack/intent) is a CLI for library maintainers. It generates, validates and ships Agent Skills inside the library's own npm package. The skills reach consumers through npm updates and stay pinned to the installed version. On the consumer side, `npx @tanstack/intent install` writes lightweight guidance blocks into AGENTS.md (the default), CLAUDE.md or .cursorrules. These blocks point at node_modules/&lt;pkg>/skills/.../SKILL.md, so the skill content itself is not copied. Evidence: Two claims merged, both voted 3-0. The announcement post (2026-03-04, Gerrard and Kyle Mathews) says: 'Skills ship inside your npm package', 'They're pinned to the installed version' and 'Update the package, and skills update too.' The TanStack AI docs show a generated mapping such as `load: node_modules/@tanstack/ai/skills/ai-core/SKILL.md`. A claim saying install 'writes their skills into' CLAUDE.md or .cursorrules was refuted 0-3, because it writes pointers and not the skill content. The mapping block may need re-running when a package adds or renames skills. TanStack AI also offers paths that do not pin to the installed version: a Claude Code plugin marketplace and `npx skills add -g`. Confidence high; vote 3-0, 3-0 (related consumer-side claim refuted 0-3). Source: https://tanstack.com/blog/from-docs-to-agents and https://tanstack.com/intent/latest and TanStack Table and TanStack AI agent-skills docs pages and https://www.npmjs.com/package/@tanstack/intent, checked 2026-11-12.
- Storybook ships MCP as the addon @storybook/addon-mcp, installed with `npx storybook add @storybook/addon-mcp`. It was introduced in Storybook 10.3 for React only, and as of 10.6 the server works in every project. The server is a local HTTP endpoint on the dev server, http://localhost:6006/mcp. It is registered with the agent host at project scope by the third-party mcp-add CLI (`npx mcp-add --type http --url ... --scope project`) or by hand; no Storybook step writes .mcp.json. Users edit AGENTS.md or CLAUDE.md by hand. A published Storybook MCP can also be hosted remotely, and Chromatic hosts it free with versioning and authorization, so teammates can use it without running Storybook. Evidence: Three claims merged, each voted 3-0. The blog post by Kyle Gach was published 2026-03-23 and modified 2026-09-11. The 10.6 docs say 'The MCP server is part of the dev server.' The 10.4 release notes (2026-05-18) describe `storybook ai setup`, which can install the addon, and say integration with agent harnesses is being made easier. Only the Storybook blog says Chromatic hosting is free. The Chromatic page names no price. Confidence high; vote 3-0, 3-0, 3-0. Source: https://storybook.js.org/blog/storybook-mcp-for-react/ and https://storybook.js.org/docs/ai/mcp/overview and https://storybook.js.org/docs/ai/setup and https://www.chromatic.com/ai, checked 2026-11-12.
- Storybook moved @storybook/addon-mcp, @storybook/mcp, its Claude and Codex plugins and their skills into the Storybook monorepo. From 10.6 these packages are versioned and released with Storybook and declare caret peer dependencies; @storybook/mcp has no Storybook dependency. Each capability is implemented once as a core toolset. The MCP addon, the hosted @storybook/mcp and a public `storybook tools` CLI are thin adapters over those toolsets. A `storybook skills get &lt;id>` CLI (PR #35757, merged into `next` on 2026-08-13) serves skill workflows from the installed Storybook, version-matched to it. It is planned to replace `storybook ai setup` and the MCP write-story-instructions tool. MCP stays supported: migration starts no earlier than 11.0 and retirement no earlier than 12.0. Evidence: Three claims merged, each voted 3-0. The tracking issue was opened 2026-07-17 and closed 2026-08-31. On npm, @storybook/addon-mcp@latest is 10.6.7, the same as storybook, with peer dependencies storybook ^10.6.7 and @storybook/addon-vitest ^10.6.7. The 10.6.0 release notes list Skills M4 and M5a. A caret range accepts any 10.x at or above 10.6.7, so it is not an exact match. The 11.0 and 12.0 dates are plans. Milestone 7, which moves the plugins to `skills get`, was blocked on other milestones. Confidence high; vote 3-0, 3-0, 3-0. Source: https://github.com/storybookjs/storybook/issues/35526 and https://github.com/storybookjs/storybook/pull/35757 and npm registry: @storybook/addon-mcp, @storybook/mcp and @storybook/react 10.6.0 release notes (newreleases.io mirror), checked 2026-11-12.
- In the Agent Skills format, a skill is a folder that contains a required SKILL.md. Its frontmatter has at least `name` (at most 64 characters, lowercase letters, numbers and hyphens) and `description` (at most 1024 characters), followed by instructions. The optional subfolders are scripts/, references/ and assets/. Optional fields include license, compatibility, metadata and the experimental allowed-tools. Evidence: Voted 3-0. The /home quote: 'a skill is a folder containing a SKILL.md file. This file includes metadata (name and description, at minimum) and instructions.' Claude Code (code.claude.com/docs; pages name versions up to v2.1.309):

- Claude Code stores MCP servers at three scopes: local (the default, "Current project only", in `~/.claude.json` under the project's path), project (`.mcp.json` in the project root, "Shared with team ... via version control") and user (`~/.claude.json`, all projects). `claude mcp add --scope project` creates or updates `.mcp.json`, whose format is a top-level `mcpServers` object; `.mcp.json` supports `${VAR}` and `${VAR:-default}` expansion. When one name is defined in several scopes, local wins over project, and project over user; fields are not merged. Source: https://code.claude.com/docs/en/mcp (sections "MCP installation scopes", "Project scope", "Scope hierarchy and precedence", "Environment variable expansion in .mcp.json"), checked 2026-11-12.
- Approval for project servers: "For security reasons, Claude Code prompts for approval in interactive sessions before using project-scoped servers from `.mcp.json` files. To reset those approval choices, run `claude mcp reset-project-choices`." An unapproved server shows as "Pending approval". A cloned repository cannot approve its own servers: `enableAllProjectMcpServers` or `enabledMcpjsonServers` committed to `.claude/settings.json` is ignored until the person accepts the workspace trust dialog. In `claude -p` runs, Agent SDK sessions and some cloud sessions, Claude Code loads project servers without asking. A server can change its tools while connected and send `list_changed`; the page documents no file watch on `.mcp.json`. Source: https://code.claude.com/docs/en/mcp (sections "Project scope", "Server status", "Project server approvals and workspace trust"), checked 2026-11-12.
- Claude Code skills follow the Agent Skills open standard. It loads them from enterprise (managed settings directory), personal `~/.claude/skills/<skill-name>/SKILL.md`, project `.claude/skills/<skill-name>/SKILL.md`, nested `<subdir>/.claude/skills/` (loaded when Claude works on files there), `--add-dir` directories, plugins (`<plugin>/skills/<skill-name>/SKILL.md`, invoked as `/plugin-name:skill-name`) and the claude.ai account. Project skills load from the start directory and each parent up to the repository root. A `<skill-name>` entry in the enterprise, personal or project location "can be a symlink to a directory elsewhere on disk". Precedence: "Enterprise over personal, and personal over project". Claude Code watches the skill directories and picks up added, edited or removed `SKILL.md` files in the session without a restart; a new top-level skills directory needs `/reload-skills`. The page names no `.agents/skills/` location and no `node_modules` location. Source: https://code.claude.com/docs/en/skills (sections "Choose where skills load", "Load skills in monorepos and subdirectories", "Live change detection"), checked 2026-11-12.
- Claude Code plugins bundle skills, agents, hooks and MCP servers; a plugin defines its servers in `.mcp.json` at the plugin root or inline in `plugin.json`, with `${CLAUDE_PLUGIN_ROOT}` for its install folder, and the servers register as `plugin:<plugin-name>:<server-name>`. A marketplace is a repository or directory with `.claude-plugin/marketplace.json`; Anthropic's official marketplace (`claude-plugins-official`) is added on the first interactive start. Marketplace sources are GitHub `owner/repo`, any git URL, a local path or a hosted `marketplace.json`. A plugin entry's `source` can be a relative path, `github`, `git-subdir`, `url`, `archive`, `npm` ("npm registry package or tarball link, fetched with your npm client and unpacked without running install scripts") or `command`. Marketplace plugins are copied into `cache/<marketplace>/<plugin>/<version>/` at install, and Claude Code installs the plugin's Node.js dependencies there. Source: https://code.claude.com/docs/en/mcp (plugin section), https://code.claude.com/docs/en/plugins, https://code.claude.com/docs/en/plugin-marketplaces, https://code.claude.com/docs/en/plugins/marketplace-reference and https://code.claude.com/docs/en/plugins/loading, checked 2026-11-12.
- Plugin scopes and approvals: user scope records the plugin in `enabledPlugins` in `~/.claude/settings.json`; project scope in the committed `.claude/settings.json`; local scope in `.claude/settings.local.json`. A committed project entry "turns the plugin on for your collaborators but doesn't download it to their machines"; each collaborator runs `claude plugin install <name>@<marketplace> --scope project` once per clone. A repository names its marketplaces in `extraKnownMarketplaces`, which needs the workspace trust dialog. A project-scope plugin "loads only after the same trust check that applies to project allow rules". `/plugin install` opens a details pane with a trust warning before the install. A personal or project skill folder with `.claude-plugin/plugin.json` loads as a plugin `<name>@skills-dir`, after the trust dialog in a project. Plugin changes apply with `/reload-plugins`. Source: https://code.claude.com/docs/en/discover-plugins ("Choose an install scope"), https://code.claude.com/docs/en/plugins/loading ("Trust check and component limits for repository plugins"), https://code.claude.com/docs/en/plugins/security ("Trust warning before you install") and https://code.claude.com/docs/en/skills, checked 2026-11-12.

Codex (developers.openai.com/codex; the pages link onward to learn.chatgpt.com; no page date):

- Codex stores MCP servers in `config.toml`: "By default this is `~/.codex/config.toml`, but you can also scope MCP servers to a project with `.codex/config.toml` (trusted projects only)." Each server is a `[mcp_servers.<server-name>]` table (stdio: `command`, `args`, `env`, `env_vars`, `cwd`; HTTP: `url`), with optional `default_tools_approval_mode` and per-tool `approval_mode`. `codex mcp add` adds a server from the CLI; `/mcp` in the TUI lists active servers. Source: https://developers.openai.com/codex/mcp, checked 2026-11-12.
- Codex reads project `.codex/config.toml` files from the project root down to the working directory (closest wins) and only when the project is trusted: "If the project is untrusted, Codex ignores project `.codex/` layers, including `.codex/config.toml`, project-local hooks, and project-local rules." Trust is set as `projects.<path>.trust_level` (`"trusted"` or `"untrusted"`) in the user config; Codex "may also start in `read-only` until you explicitly trust the working directory (for example, via an onboarding prompt or `/permissions`)" (security page). Source: https://developers.openai.com/codex/config-basic, https://developers.openai.com/codex/config-advanced, https://developers.openai.com/codex/config-reference and https://developers.openai.com/codex/agent-approvals-security, checked 2026-11-12.
- Codex reads skills from repository, user, admin and system locations: `.agents/skills` in each directory from the working directory up to the repository root, `$HOME/.agents/skills` and `/etc/codex/skills`. "Codex supports symlinked skill folders and follows the symlink target when scanning these locations." "Codex detects skill changes automatically. If an update doesn't appear, restart Codex." The page names no `.codex/skills` and no `node_modules` location. Source: https://developers.openai.com/codex/skills, checked 2026-11-12.
- Codex plugins: a plugin has a portable `plugin.json` at its root (Agent Plugins format) or the compatibility `.codex-plugin/plugin.json`, with optional `.mcp.json` and skills. Marketplace files: `$REPO_ROOT/.agents/plugins/marketplace.json` (repo), `~/.agents/plugins/marketplace.json` (personal) and the "legacy-compatible" `$REPO_ROOT/.claude-plugin/marketplace.json`; `codex plugin marketplace add` takes GitHub, git or local sources. Entry sources include local paths, `url`, `git-subdir` and `npm` (`package`, optional `version` range, optional HTTPS `registry`; "Codex downloads the package without running lifecycle scripts"). Plugins install into `~/.codex/plugins/cache/$MARKETPLACE_NAME/$PLUGIN_NAME/$VERSION/` and load from that copy. A repository enables a plugin with `[plugins."<plugin>@<marketplace>"] enabled = true` in its `.codex/config.toml`, which loads only in a trusted project. In Codex CLI, `/plugins` opens the browser, and a new session is needed before the bundled skills are used. Source: https://developers.openai.com/plugins/build/plugins and https://developers.openai.com/codex/plugins, checked 2026-11-12.

Cursor (cursor.com/docs; no page date):

- Cursor reads MCP servers from `.cursor/mcp.json` in the project and `~/.cursor/mcp.json` for all projects; both use a top-level `mcpServers` object, with `${env:NAME}`, `${userHome}`, `${workspaceFolder}` and similar interpolation, and `envFile` for stdio servers. "Cursor asks for approval before using MCP tools by default." The page documents no separate approval of a project's `.cursor/mcp.json` before the server starts, and no reading of Claude Code's `.mcp.json`. For changes to a custom server: "update your local files and restart Cursor"; for npm-based servers, remove the server, clear the npm cache and add it again. Source: https://cursor.com/docs/mcp (sections "Project Configuration", "Global Configuration", "Tool approval", FAQ), checked 2026-11-12.
- Cursor loads skills from `.agents/skills/` and `.cursor/skills/` (project), `~/.agents/skills/` and `~/.cursor/skills/` (user), and "for compatibility" from `.claude/skills/`, `.codex/skills/`, `~/.claude/skills/` and `~/.codex/skills/`. A `.cursor/skills/` or `.agents/skills/` folder anywhere in the repository is also found and scoped to files in that folder. "When Cursor starts, it automatically discovers skills from skill directories." "Skills aren't imported on their own": to bring skills from GitHub, package them in a plugin. The page names no `node_modules` location. Source: https://cursor.com/docs/skills, checked 2026-11-12.
- Cursor plugins come in two formats: Agent Plugins (root `plugin.json`, skills and MCP servers) and Cursor Plugins (`.cursor-plugin/plugin.json`, also rules, agents, commands and hooks). The Cursor Marketplace lists official plugins, distributed as Git repositories, each "manually reviewed" before listing; Teams and Enterprise can import team marketplaces from a repository with `.cursor-plugin/marketplace.json`, with the modes Default Off, Default On and Required. Install is in Customize, where the person picks project or user scope. Local plugins load from `~/.cursor/plugins/local` after a restart or "Developer: Reload Window"; a symlink there loads only when its target is inside that folder. MCP servers can also be shared as `cursor://anysphere.cursor-deeplink/mcp/install?...` links. Source: https://cursor.com/docs/plugins, checked 2026-11-12.

VS Code with GitHub Copilot (microsoft/vscode-docs, `DateApproved: 11/11/2026` on each page; last commits 2026-11-10 to 2026-11-12):

- For the Copilot harness, VS Code now reads MCP servers natively from two files with a top-level `mcpServers` object: `$COPILOT_HOME/mcp-config.json` or `~/.copilot/mcp-config.json` (user, shared with Copilot CLI) and `.mcp.json` at the workspace root (team). Existing `.vscode/mcp.json` entries can be forwarded to Copilot sessions when eligible; entries that need `${input:...}` or `${command:...}` are rejected. The portable format uses `${NAME}` or `${NAME:-default}`; the editor format uses `${env:NAME}`, `envFile` and `inputs`. Source: https://code.visualstudio.com/docs/agents/reference/mcp-configuration (repository file docs/agents/reference/mcp-configuration.md), checked 2026-11-12.
- Trust in VS Code: "Workspace `.vscode/mcp.json` and `.mcp.json` configurations inherit Workspace Trust. Restricted mode prevents these servers from starting. In a trusted workspace, they can start without a separate MCP trust prompt, including after configuration changes." Non-workspace sources may prompt on first start or after a change; **MCP: Reset Trust** resets those decisions. Tool calls have separate approvals. Source: https://code.visualstudio.com/docs/agents/run/manage-mcp-servers ("MCP server trust"), checked 2026-11-12.
- VS Code skill locations per harness: Copilot, project `.github/skills/` and personal `~/.copilot/skills/`; Claude, `.claude/skills/` and `~/.claude/skills/`; Codex, `.agents/skills/` and `~/.agents/skills/`. The deprecated Local harness also reads `.claude/skills/`, `.agents/skills/` and their home equivalents, and the deprecated `chat.agentSkillsLocations` setting adds locations for Local sessions. The `name` must match the parent folder name, or the skill does not load. VS Code extensions can contribute skills through the `chatSkills` contribution point in their `package.json`. The page names no `node_modules` location. Source: https://code.visualstudio.com/docs/agent-customization/agent-skills, checked 2026-11-12.
- VS Code agent plugins (setting `chat.plugins.enabled`) bundle skills, agents, MCP servers and hooks. A marketplace is a Git repository; defaults named are github/copilot-plugins and github/awesome-copilot, and `chat.plugins.marketplaces` adds more. "The first time you install a plugin from a new marketplace, VS Code shows a trust prompt." Gemini CLI (google-gemini/gemini-cli at tag v0.68.0, released 2026-11-10):

- Gemini CLI reads MCP servers from the `mcpServers` object of its `settings.json` files: user `~/.gemini/settings.json`, project `.gemini/settings.json`, plus system defaults and system override files; project settings override user settings. Remote servers use `url` (SSE) or `httpUrl` (streamable HTTP). `"trust": true` on a server "bypasses all tool call confirmations"; otherwise tool calls ask. `gemini mcp add` writes the server, with `-s, --scope` user or project and the default "project". `/mcp reload` reloads all MCP servers. Source: https://github.com/google-gemini/gemini-cli/blob/v0.68.0/docs/tools/mcp-server.md, .../docs/reference/configuration.md and .../docs/reference/commands.md, checked 2026-11-12.
- Folder trust in Gemini CLI "is **disabled by default**" and is enabled with `security.folderTrust.enabled`. When it is on, an untrusted folder runs in safe mode: the project `.gemini/settings.json` is not loaded, "MCP servers do not connect", and extensions cannot be installed, updated or removed. Source: https://github.com/google-gemini/gemini-cli/blob/v0.68.0/docs/cli/trusted-folders.md, checked 2026-11-12.
- Gemini CLI finds skills, lowest to highest precedence, in built-in skills, extension skills, user `~/.gemini/skills/` or `~/.agents/skills/`, and workspace `.gemini/skills/` or `.agents/skills/`; within a tier, the `.agents/skills/` alias wins. `gemini skills install <url> [--scope workspace]` installs (user by default) and asks to confirm a remote source; `gemini skills link <path>` links a local skill; `/skills reload` rescans. Each activation of a skill asks the person for consent. Source: https://github.com/google-gemini/gemini-cli/blob/v0.68.0/docs/cli/skills.md and .../docs/cli/using-agent-skills.md, checked 2026-11-12.
- Gemini CLI extensions package prompts, MCP servers, commands, hooks, sub-agents and skills (`skills/<name>/SKILL.md`) behind a `gemini-extension.json` manifest. Extensions load from `~/.gemini/extensions`; `gemini extensions install <GitHub URL or local path>` "creates a copy of the extension during installation", and `gemini extensions update` pulls changes. Install asks for confirmation unless `--consent` is given. Extensions are enabled globally by default and can be disabled per user or workspace. The gallery at geminicli.com/extensions/browse indexes public repositories with a root `gemini-extension.json`. No npm source is documented. Source: https://github.com/google-gemini/gemini-cli/blob/v0.68.0/docs/extensions/reference.md, .../docs/extensions/index.md and .../docs/extensions/releasing.md, checked 2026-11-12.
