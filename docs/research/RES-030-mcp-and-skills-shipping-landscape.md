# RES-030: How libraries ship MCP servers and agent skills, and how agent hosts find them

<!-- Add outcome: answered, partial or blocked to frontmatter when an answer or a block is known. Only answered work can become resolved. -->

## Question
How do other libraries ship MCP servers and agent skills (inside the library package or apart), how do they install them into a consumer project, and how do agent hosts find them?

## Answer
Answered. The sweep of 2026-11-12 established where Ant Design, shadcn/ui, Chakra UI, MUI, Nuxt UI, Storybook and TanStack Intent ship their MCP servers and skills, how each installs them, which host files the installs write, how each keeps versions in step, and what the Agent Skills format requires. Two single research agents then closed the open parts on 2026-11-12. Question 1 covered the six hosts' own documentation (Findings, "Agent hosts, from their own documentation"). Question 2 covered Tailwind CSS, Astro, Mantine, Vercel and Figma, the files of `antd setup`, and how in-package skills reach a project again after an update (Findings, "Libraries, antd setup and update behaviour"). Every part of the sufficient-answer condition now has confirmed findings; the uncovered details are listed under "Not covered by any source read" below.

- node_modules: no host's documentation names `node_modules` as a place where it finds skills or MCP server definitions. A package's skills reach a host only through a host folder (a copy, or a symlink where the host documents symlinks: Claude Code and Codex), a plugin, or a VS Code extension. The Agent Skills client guide tells clients to skip `node_modules/`. Claude Code and Codex plugin marketplaces can fetch a plugin from an npm package, which they copy into their own plugin cache.
- `.agents/skills/` is read by Codex, Cursor, Gemini CLI and Devin, and by VS Code's Codex harness. Claude Code's skills page does not name it.
- Refresh after a change: Claude Code, Codex, Cursor (skills at start) and Gemini CLI (`/skills reload`) pick up skill changes; Cursor needs a restart for changed MCP servers; Gemini CLI has `/mcp reload`; VS Code starts trusted workspace servers again after a change without a prompt. What Codex and Devin do after an edit to an MCP config file is not documented in the pages read.

Disagreements and corrections:

- The earlier library-side finding gives VS Code `.vscode/mcp.json` with `servers`. VS Code's own docs (DateApproved 11/11/2026) call that the deprecated Local format and name workspace-root `.mcp.json` and `~/.copilot/mcp-config.json` with `mcpServers` for Copilot.
- The earlier finding gives Windsurf `~/.codeium/windsurf/mcp_config.json`. Windsurf's docs now redirect to Devin Desktop, which uses `.devin/mcp_config.json` and `~/.config/devin/mcp_config.json` and only imports the Codeium file.
- Skill precedence: the Agent Skills guide says project skills override user skills, and Gemini CLI agrees (workspace highest). Claude Code says "personal over project".
- Codex's project `.codex/config.toml`, which shadcn's docs say the CLI cannot write and a third-party guide said exists, is confirmed by Codex's own docs, for trusted projects only.

Not documented in the pages read: the edit date of the Claude Code, Codex, Cursor and Devin pages; a separate approval of a project's `.cursor/mcp.json` server in Cursor; npm as a plugin source in Cursor, VS Code, Gemini CLI or Devin; a marketplace for Devin agent plugins. This run did not read modelcontextprotocol.io; each host's own pages define its configuration files.

### What `antd setup` writes (question 2b)

|---|---|---|---|---|
| claude | mcp (default), skill, both | `.mcp.json`, `mcpServers` | `.claude/skills/antd/` | `CLAUDE.md` |
| cursor | mcp (default), skill, both | `.cursor/mcp.json`, `mcpServers` | `.agents/skills/antd/` | `AGENTS.md` |

### Disagreements and corrections from question 2
- Intent mapping. The earlier finding quotes the TanStack AI docs with `load: node_modules/@tanstack/ai/skills/ai-core/SKILL.md`. The Intent 0.5.6 docs and code write `intent load <package>#<skill>` commands and say the block "does not store load paths".
- Storybook skills command. The earlier finding names `storybook skills get <id>` (PR #35757). The shipped 10.6.7 CLI and the 11.0 migration notes use `storybook skills <id>`.
- Storybook skill source. The earlier finding says skills are served from the installed Storybook. That holds for 10.6.7. In 11.0.0-beta.2, the skill files come from GitHub at the version's tag, and each skill then tells the agent to run `npx storybook skills <id>` against the installed Storybook.
- Ant Design version. The refuted claim said the server is not tied to the project. The code shows both sides: `npx -y @ant-design/cli` takes the latest CLI, while the antd data version follows `node_modules/antd` unless `--version` is given.
- Which instruction file Claude Code reads. The Next.js guide says Claude Code reads `AGENTS.md` at session start. The Storybook 11 migration notes say Claude Code reads `CLAUDE.md` "instead", and Storybook also writes its section there. This run did not recheck Claude Code's own memory docs.
- VS Code config. Mantine's guide, Figma's guide and `antd setup` still write `.vscode/mcp.json` with `servers`; VS Code's own docs call that the deprecated Local format (question 1).

### What the run established
The summary of the run's report, in its own words:

> As of November 2026, the libraries checked ship MCP servers and agent skills in four ways. 1. A separate npm package run through npx: MUI uses @mui/mcp, Chakra UI uses @chakra-ui/react-mcp and Ant Design uses @ant-design/cli. 2. A subcommand of the library's existing CLI: shadcn runs `shadcn mcp`. 3. A hosted HTTP server: Nuxt UI runs one at ui.nuxt.com/mcp, and Chromatic can host a published Storybook MCP. 4. A dev-server addon released together with the library: Storybook's @storybook/addon-mcp. Agent skills come either from GitHub through the third-party skills CLI (Nuxt UI and Chakra UI) or inside the library's own npm package (the TanStack Intent model). Installation ranges from fully manual edits to each agent host's config (MUI, Chakra UI and Nuxt UI) to an init or setup command that writes project files for named clients: `shadcn mcp init --client ...` and `antd setup --client claude|cursor|vscode|codex --mode mcp|skill|both`. Storybook uses the third-party mcp-add CLI. The config files named are .mcp.json (Claude Code), .cursor/mcp.json, .vscode/mcp.json (under a `servers` key), ~/.codex/config.toml (user level, which shadcn's CLI cannot write), ~/.gemini/settings.json, Windsurf's mcp_config.json and ~/.copilot/mcp-config.json. Version alignment also varies. MUI's documented config floats on @latest, and Nuxt UI's hosted server is not tied to any installed version. TanStack Intent skills live in node_modules, so they are pinned to the installed version and change with npm update. From 10.6, Storybook releases its MCP packages with Storybook itself, uses caret peer dependencies, and serves version-matched skills from the installed Storybook through `storybook skills get`.

### The question sent to the workflow
> As of November 2026, how do UI component libraries and developer tools ship MCP (Model Context Protocol) servers and agent skills for coding agents? (1) Where do they ship them: inside the library's own npm package, as separate packages, or as hosted servers? Name concrete projects and what each does, for example shadcn/ui, Chakra UI, MUI, Ant Design, Mantine, Storybook, Astro, Tailwind CSS, TanStack (including TanStack Intent), Nuxt UI, Vercel and Figma. (2) How do they install the server and the skills into a consumer project: an init command or a package.json bin script, and which files it writes, such as .mcp.json, AGENTS.md, CLAUDE.md, .claude/skills or .cursor/rules? (3) How do agent hosts find MCP servers and skills: Claude Code, Codex, Cursor, VS Code Copilot, Gemini CLI and Windsurf, including configuration files, plugins and marketplaces, and the Agent Skills format? ## Findings
- Ant Design's official MCP server is not in the antd component package. It ships in the separate @ant-design/cli package (v6.3.5 or later) and starts with `antd mcp` (or `npx -y @ant-design/cli mcp`), which provides 8 tools and 2 prompts. The same CLI has `antd setup --client &lt;claude|cursor|vscode|codex>`, which writes project configuration in three modes (mcp, skill or both) and takes --dry-run, --check and --write-instructions flags. Evidence: Two claims merged, both voted 3-0. The quote: 'Starting from @ant-design/cli v6.3.5, you can launch an official MCP server with the antd mcp command, providing 8 tools and 2 prompts.' The npm registry shows that antd defines no bin, while @ant-design/cli defines bin { antd: 'dist/index.js' } (v6.7.0, 2026-11-04). The docs show the setup examples and list the supported clients and modes. They do not say which files setup writes or what --check and --write-instructions do. A server-side --version argument pins the antd version the docs data comes from. Confidence high; vote 3-0, 3-0. Source: https://ant.design/docs/react/mcp/, checked 2026-11-12.
- shadcn/ui's MCP server is the `mcp` subcommand of the shadcn CLI package (`npx shadcn@latest mcp`). It is not a separately named package. It browses, searches and installs items from shadcn-compatible registries configured in the consumer's components.json. `npx shadcn@latest mcp init --client claude|cursor|vscode|codex|opencode` runs in the project, and the docs place the config in .mcp.json for Claude Code, .cursor/mcp.json for Cursor and .vscode/mcp.json for VS Code with Copilot. For Codex the CLI cannot write ~/.codex/config.toml. It installs the dependency and prints manual steps. Evidence: Three claims merged, each voted 3-0. Docs quote: 'The MCP server acts as a bridge between your AI assistant, component registries and the shadcn CLI.' Docs quote on Codex: 'The shadcn CLI cannot automatically update ~/.codex/config.toml.' In the CLI source, the codex branch installs shadcn, prints instructions and exits without calling runMcpInit, even though the CLIENTS table lists configPath .codex/config.toml. npm shows shadcn 4.23.0 with the single bin `shadcn`. A third-party guide (shadcn.io) says Codex also reads a project-level .codex/config.toml in trusted projects. The official shadcn docs do not say this. Confidence high; vote 3-0, 3-0, 3-0. Source: https://ui.shadcn.com/docs/mcp and https://github.com/shadcn-ui/ui (packages/shadcn/src/commands/mcp.ts; apps/v4/content/docs/(root)/mcp.mdx), checked 2026-11-12.
- Chakra UI ships its MCP server as the separate npm package @chakra-ui/react-mcp. The server supports only stdio. Installation is manual, one host at a time: a server block that runs `npx -y @chakra-ui/react-mcp` goes in .vscode/mcp.json (servers key), .cursor/mcp.json, ~/.codeium/windsurf/mcp_config.json or a custom client (mcpServers key), or Zed settings.json (context_servers). For Claude Code the user runs `claude mcp add`. Chakra documents no init or bin script. Skills are installed separately from GitHub with the third-party `npx skills add` CLI. Evidence: Two claims merged, both voted 3-0. The quote: 'The MCP server currently supports only stdio transport and is published at @chakra-ui/react-mcp.' The latest npm version is 2.1.1, published about a year ago, with 9 versions. The two sources disagree on tool names. The docs list list_components and list_component_templates. The npm README lists get_components and list_blocks. Confidence high; vote 3-0, 3-0. Claude Code (code.claude.com/docs; pages name versions up to v2.1.309):
