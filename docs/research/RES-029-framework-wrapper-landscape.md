Common points: every generated React wrapper in the five libraries that ship one is a call to `@lit/react`'s `createComponent` (Stencil and therefore Ionic through `@stencil/react-output-target/runtime`; Ionic's hand-written components use its own `createReactComponent`). `createComponent` sets each prop that is `in` the element class prototype as a property in a layout effect after render, passes the other props to React, maps listed event props to `addEventListener`, rewrites `className` to `class`, forwards the ref to the element, and passes children through as light DOM children. Each library exports one flat named component per custom element tag; no source read exports a compound component with dot members such as `Steps.Root`. The event-prop names differ: Lit's generator and Stencil use `on` plus PascalCase of the event name, Web Awesome and Shoelace `on` plus PascalCase including the prefix (`onWaChange`), and Spectrum the camelCased event name without `on` (`change`, `spMenuItemAdded`).

No library among the six ships a wrapper package for Preact or Solid. Stencil generates JSX type declarations for both; Web Awesome and Shoelace give Preact users one note about `preact/compat` types; the others say nothing.

Not covered by any source read (UNVERIFIED either way): a test of any wrapper under Preact (including `preact/compat`) or Solid; a test of `@lit/react` under React 19 (its devDependencies are React 18.2 and its peer range covers `@types/react` 17 to 19); a slot test in `@lit/react`'s own suite (its children test checks text and element children only); and how Fluent UI 3 expects React users to use its elements, since its repository docs say only that it works "with any modern JavaScript framework".

What the run of 2026-11-12 on question 1 found, from React 19.3.1 source and tests and from Redact 0.3.1 source:

- React 19 property rule: for a tag with a dash (or an `is` prop), React assigns a prop as a property when `name in node` is true at the moment React writes it; otherwise it writes an attribute, with `true` as an empty attribute and `false`, `undefined`, functions and symbols as no attribute. `in` also finds accessors on the prototype, so it is not limited to names set "during construction". The two refuted claims were each half right: react.dev does say "By default, React will pass values bound in JSX as attributes" and gives the `"1,2,3"` example, but that default applies only when the name is not on the element; and react.dev's "shows up on the class during construction" is narrower than the source, which checks `in` on every write.
- React 19 events: a function prop that starts with `on` and is not a React event name becomes `addEventListener` with the exact rest of the name (case and dashes kept), and a `Capture` suffix gives a capture listener. React's own event names (`onClick`, `onChange`, `onInput` and the rest) stay on React's delegated event system for custom elements too.
- React 19 TypeScript: `@types/react` 19.3.0 has no index signature in `JSX.IntrinsicElements`, so each custom tag must be declared by module augmentation of `react` (or `react/jsx-runtime` for `"jsx": "react-jsx"`), as the React 19 upgrade guide shows.
- React 19 refs: a ref on a host element receives the DOM element itself.
- React 19 children and slots: children are appended as light DOM children of the custom element before it is connected; `slot="…"` reaches the DOM as the `slot` attribute; a Fragment adds no DOM element.
- Redact 0.3.1 handles custom elements differently from React 19. Its one prop writer (`setProp`) has no custom element branch: apart from seven named form properties (`value`, `checked`, `selected`, `disabled`, `multiple`, `muted`, `readonly`), it writes every prop as an attribute with a lower-cased name and a string value, so an array becomes `"1,2,3"` and an object `"[object Object]"`. It lower-cases event names (`onsayHi` listens for `sayhi`, where React listens for `sayHi`) and attaches every `on…` prop, `onChange` included, as a direct listener on the element. Its own JSX namespace accepts any tag and any props. No Redact document, README or test states custom element behaviour; this answer rests on its source at the 0.3.1 release commit.

UNVERIFIED (derived, not observed): a Lit element defined before React renders it is upgraded inside `document.createElement`, so its reactive properties are found by `in` on the first write; an element defined later gets attributes on the first render and properties on later writes. A browser test would have to observe both orders.

Not observed in any run (the test that would settle it): run one Lit element through React 19.3.1 and through Redact 0.3.1 in a real browser and observe (1) whether an array and an object prop arrive as properties (`el.items === array`) or as attributes (`getAttribute('items')`); (2) whether a camelCase prop reaches the camelCase property; (3) whether `onacme-change` and a camelCase event name each call the handler; (4) whether `onChange` fires for a non-bubbling `change` event; (5) what a ref holds; (6) whether children and `slot` attributes match. The Custom Elements Everywhere suite, run against Redact, would observe most of these.

## Findings
- React (the current React 19 docs) listens for a custom element's CustomEvents through an on-prefixed JSX prop that keeps the exact event name: onspeak listens for 'speak', and onsay-hi listens for 'say-hi'. The verifier noted that React 18 and earlier did not attach these listeners; a ref plus addEventListener was needed. Evidence: The react.dev section 'Listening for events on custom elements' gives the example &lt;my-element onspeak={e => ...}> and says event names are case-sensitive. The React 18 limit comes from the verifier's own knowledge, not from the page. Confidence high; vote 3-0. Source: https://react.dev/reference/react-dom/components, checked 2026-11-12.
- How React chooses between a property and an attribute on a custom element is unresolved. Two claims were refuted: that React passes values as attributes by default and turns non-strings into strings (vote 1-2), and that React sets a property only when the name exists on the instance during construction (vote 0-3). Evidence: Both statements were voted down against the same react.dev page. No replacement wording survived. Confidence low; vote refuted 1-2 and 0-3. Source: https://react.dev/reference/react-dom/components, checked 2026-11-12.
- Preact (the v10 guide) decides for each prop whether to set a DOM property or an attribute by inspecting the element. When the element defines a setter for that name, Preact uses the property. Preact never changes the case of a prop name, so someProperty must be spelled exactly; someproperty and some-property do not work. The v11 guide has the same naming note. Evidence: The guide text was quoted word for word. The v10 page carries a banner saying v11 is current (v11.2.0 is linked). From memory of Preact's source, a verifier said the real check is 'name in dom', which matches any property, not only setters, and works only once the element is upgraded. The verifier did not re-check this. Confidence high; vote 3-0 (both claims). Source: https://preactjs.com/guide/v10/web-components/ and https://preactjs.com/guide/v11/web-components, checked 2026-11-12.
- Preact registers an event prop it does not recognize with the exact casing written after 'on'. onTabChange listens for 'TabChange', and ontabchange listens for 'tabchange'. Evidence: The v10 guide gives this exact example. The vote was split, and nobody confirmed whether v11 behaves the same way. Confidence medium; vote 2-1. Source: https://preactjs.com/guide/v10/web-components/, checked 2026-11-12.
- In server rendering with preact-render-to-string, complex property values such as objects are not automatically serialized into the HTML. They reach the element only when the client hydrates. Evidence: The guide sentence was quoted word for word. Nobody checked what the renderer actually writes for such a value. Confidence high; vote 3-0. Source: https://preactjs.com/guide/v10/web-components/, checked 2026-11-12.
- In Preact v11 TypeScript, an undeclared custom element tag is a type error: "Property 'loading-bar' does not exist on type 'JSX.IntrinsicElements'". The guide says module augmentation is needed: declare global { namespace preact.JSX { interface IntrinsicElements { 'loading-bar': {...} } } }, with export {} in the file. Evidence: The official v11 TypeScript guide, section 'Extending IntrinsicElements for custom elements'. The page carries no date. Confidence high; vote 3-0 (two duplicate claims merged). Source: https://preactjs.com/guide/v11/typescript/, checked 2026-11-12.
- In Solid, attr:name={value} forces a value to be written as an attribute, with the prefix stripped (&lt;my-element attr:status={value} />). prop: forces property assignment and keeps objects and arrays as they are. bool: appears in examples. Types come from augmenting JSX.ExplicitProperties, ExplicitAttributes and ExplicitBoolAttributes in the 'solid-js' module. In the DOM runtime, null or undefined removes the attribute, and server rendering writes the stripped name with an escaped value. Evidence: The attr reference page was last updated 4/28/26. The TypeScript page shows &lt;my-web-component attr:name attr:count bool:disabled>. A verifier added a nuance: the docs type 'count' as a number for attr:, so attr: accepts values that are not strings, and the attribute itself ends up as a string. Confidence high; vote 3-0 (three claims merged). Source: https://docs.solidjs.com/reference/jsx-attributes/attr and https://docs.solidjs.com/configuration/typescript, checked 2026-11-12.
- In Solid, custom events are attached with on:Name. They are typed by augmenting JSX.CustomEvents, where the key matches the name exactly. Native events used with on: also need CustomEvents to be extended. Since v1.9.0, a handler can be an object that carries listener options. Evidence: Quoted from the official docs. The vote was split, and the docs describe Solid 1.x. Nobody checked whether a Solid 2.x pre-release changes on:. Confidence medium; vote 2-1. Source: https://docs.solidjs.com/configuration/typescript, checked 2026-11-12.
- The open-wc Custom Elements Manifest analyzer page lists community tools that read the manifest. cem-plugin-reactify and custom-element-react-wrappers generate React wrappers. custom-element-jsx-integration generates JSX types for projects that use JSX but not React. custom-element-solidjs-integration generates SolidJS types. The two integration tools generate types only, not wrappers. Evidence: The page's Community Plugins table, scraped live. Outside authors add entries by pull request, so a listing does not mean the tool is endorsed or maintained. Confidence high; vote 3-0 (two claims merged). Source: https://custom-elements-manifest.open-wc.org/analyzer/plugins/intro/, checked 2026-11-12.
- TanStack publishes TanStack Redact in the TanStack/redact GitHub repository, created 2026-04-20, as npm @tanstack/redact. The latest version is 0.3.1, published 2026-11-04T05:08Z, out of 18 GitHub releases. The 'next' dist-tag still points to 0.0.19. Releases come quickly, from 0.2.2 on 10-28 to 0.3.1 on 11-04. The project began as 'tanstack-dom', whose alpha packages @tanstack/react, @tanstack/react-dom and others were published under the next tag. Evidence: Checked against the live npm registry and the GitHub API on 2026-11-12. The npm maintainers are tannerlinsley, alemtuzlak and kevinvandy. Confidence high; vote 3-0 (three claims merged). Source: https://www.npmjs.com/package/@tanstack/redact and https://github.com/tanstack/redact, checked 2026-11-12.

The README says Redact is 'not a new direction for React or a replacement for the project'. Tanner Linsley's launch post (2026-10-26) calls it 'a smaller replacement for React and React DOM in the browser' that needs no change to application code. Evidence: The wording differs between sources. 'Not a replacement' refers to the React project. 'Drop-in replacement' and 'smaller replacement' refer to the react and react-dom modules; the repository's first commit uses 'drop-in replacement'. 'No change to application code' is TanStack's own statement and has not been tested independently. Confidence high; vote 3-0, 3-0 and 2-1 (claims merged). Source: https://www.npmjs.com/package/@tanstack/redact and https://github.com/tanstack/redact and https://tanstack.com/blog/introducing-tanstack-redact, checked 2026-11-12.
- The sources disagree on Redact's compatibility. The repository's About text claims 'An alternative logical projection of React with 100% API compliancy'. The README and the compatibility docs say 'API availability is not a promise of every React behavior'. They also say React's APIs and behavior are the reference, but the default Vite setup renders synchronously. Listed exceptions: no time slicing, interruptible renders or priority scheduling (transitions, Activity, Suspense); full Fizz prerender and resume APIs are not implemented; legacy class lifecycles and the Profiler callback do nothing; the deprecated ReactDOM.render, ReactDOM.hydrate, unmountComponentAtNode and findDOMNode are not implemented. Evidence: The repository was fetched live at commit 782d829 (2026-11-11), and the compatibility page (v0) on 2026-11-12. Confidence high; vote 3-0 (two claims merged). Source: https://github.com/tanstack/redact and https://tanstack.com/redact/latest/docs/compatibility, checked 2026-11-12.

Redact takes over only hydration and client rendering. The Next.js integration uses withRedact and keeps react and react-dom installed. Evidence: The launch post and the official Next.js integration page say the same thing. Confidence high; vote 3-0. Source: https://tanstack.com/blog/introducing-tanstack-redact and https://tanstack.com/redact/latest/docs/next, checked 2026-11-12.

Commands: REACT_VERSION=18.3.1 pnpm test:react18 and pnpm test:compatibility:size. This is the only testing practice in the evidence; the page does not publish results. Evidence: Quoted word for word from the v0 docs. The page describes what the tests cover, not their results. It says nothing about custom elements. Confidence high; vote 3-0. React 19, which tags count as custom elements:
- React treats a tag as a custom element when its name contains a dash, except the eight reserved SVG and MathML names (`annotation-xml`, `color-profile`, `font-face`, `font-face-src`, `font-face-uri`, `font-face-format`, `font-face-name`, `missing-glyph`). react.dev adds that a built-in element with an `is` prop is treated as a custom element too. Source: https://github.com/facebook/react/blob/v19.3.1/packages/react-dom-bindings/src/shared/isCustomElement.js and https://react.dev/reference/react-dom/components#custom-html-elements (etag `"938b2427ba51cd21e8dcd06a8b009b1f"`), checked 2026-11-12.

React 19, property or attribute (settles the two refuted claims):
- The deciding passage is `setValueForPropertyOnCustomComponent`. After the event branch it runs: `if (name in (node as any)) { (node as any)[name] = value; return; } if (value === true) { node.setAttribute(name, ''); return; } // From here, it's the same as any attribute setValueForAttribute(node, name, value);`. So a prop becomes a property when the name is `in` the element (own property or anywhere on the prototype chain) at the time of the write, and an attribute otherwise. The check runs on the first render and on every update. Source: https://github.com/facebook/react/blob/v19.3.1/packages/react-dom-bindings/src/client/DOMPropertyOperations.js#L198-L243, checked 2026-11-12.
- On the attribute path, `null`, `undefined`, functions and symbols remove the attribute; `false` removes it unless the name starts with `data-` or `aria-`; any other value is written as `'' + value`, so `[1,2,3]` becomes `"1,2,3"`. The attribute name keeps the JSX spelling; React applies no alias (`arabicForm` stays `arabicForm`, not `arabic-form`). Source: https://github.com/facebook/react/blob/v19.3.1/packages/react-dom-bindings/src/client/DOMPropertyOperations.js#L106-L140 and the test "should not apply React-specific aliases to custom elements", https://github.com/facebook/react/blob/v19.3.1/packages/react-dom/src/__tests__/ReactDOMComponent-test.js#L833-L850, checked 2026-11-12.
- `setPropOnCustomElement` handles `style`, `dangerouslySetInnerHTML`, string or number `children`, `onScroll`, `onScrollEnd` and `onClick` itself, ignores `ref`, `innerHTML`, `innerText`, `textContent`, `suppressContentEditableWarning` and `suppressHydrationWarning`, leaves every name in React's event registry (`registrationNameDependencies`) to React's event system, and sends every other prop to `setValueForPropertyOnCustomComponent`. On mount it skips `undefined` values; on update, a prop that disappears is written as `undefined` (so a property is set to `undefined`). Source: https://github.com/facebook/react/blob/v19.3.1/packages/react-dom-bindings/src/client/ReactDOMComponent.js#L1002-L1107, #L1462-L1481 and #L1960-L1995, checked 2026-11-12.
- React's own tests pin the rule: with no property, `foo={true}` gives `foo=""` and `foo={false}` removes it ("boolean props should not be stringified in attributes"); once an accessor exists, values are assigned unconverted, including `true`, `false`, `null` and functions ("values should not be converted to booleans when assigning into custom elements", "custom element properties should accept functions"); assigning the property does not remove an attribute written earlier ("assigning to a custom element property should not remove attributes"). The tests run in jsdom with tags that are never defined; they install accessors with `Object.defineProperty` "to activate the `in` heuristic". Source: https://github.com/facebook/react/blob/v19.3.1/packages/react-dom/src/__tests__/DOMPropertyOperations-test.js#L1084-L1350, checked 2026-11-12.
- Initial props are written in `finalizeInitialChildren` → `setInitialProperties`, right after `ownerDocument.createElement(type)` (or `createElement(type, {is})`) and while the element is still disconnected; React's comment says initial children "are appended while disconnected". Source: https://github.com/facebook/react/blob/v19.3.1/packages/react-dom-bindings/src/client/ReactFiberConfigDOM.js#L620-L628 and #L695-L709, checked 2026-11-12.
- react.dev states the rule in narrower words. It says "By default, React will pass values bound in JSX as attributes", "Non-string JavaScript values passed to custom elements will be serialized by default" (`[1,2,3]` → `"1,2,3"`), and "React will, however, recognize a custom element's property as one that it may pass arbitrary values to if the property name shows up on the class during construction". The React 19 release post says: "props that match a property on the Custom Element instance will be assigned as properties, otherwise they will be assigned as attributes", and that React 19 "passes all tests on Custom Elements Everywhere". Disagreement: react.dev's "during construction" against the source's `in` check on each write, which also finds prototype accessors and properties added later; the release post's wording matches the source. Source: https://react.dev/reference/react-dom/components#attributes-vs-properties (etag `"938b2427ba51cd21e8dcd06a8b009b1f"`) and https://react.dev/blog/2024/12/05/react-19#support-for-custom-elements (etag `"a75a46b16ea010f95a36294f3563b130"`), checked 2026-11-12.

React 19, custom events:
- For a custom element, a prop whose name starts with `on` and whose value is a function, and which is not a React event name, becomes `node.addEventListener(name.slice(2), value, useCapture)`, where a `Capture` suffix is cut off and sets `useCapture`. The old listener is removed on change. The name is not lower-cased. A non-function `on…` value is handled as an ordinary property or attribute. Source: https://github.com/facebook/react/blob/v19.3.1/packages/react-dom-bindings/src/client/DOMPropertyOperations.js#L198-L227, checked 2026-11-12.
- React's tests: `oncustomevent` hears `customevent`, `onCustomevent` hears `Customevent`, `oncustom-event` hears `custom-event`, and capture listeners work. `onClick`, `onChange` and `onInput` on a custom element go through React's synthetic events (the tests check `syntheticClickEvent.nativeEvent` and dispatch `change` and `input` with `bubbles: true`). Source: https://github.com/facebook/react/blob/v19.3.1/packages/react-dom/src/__tests__/DOMPropertyOperations-test.js#L263-L520 and #L1003-L1026, checked 2026-11-12.

React 19, TypeScript JSX types:
- `@types/react` 19.3.0 declares `JSX.IntrinsicElements` as a list of HTML and SVG tags with no index signature, so a custom tag is not typed until it is declared. `react/jsx-runtime` re-exports the same `JSX`. Source: `@types/react` 19.3.0 tarball, `index.d.ts` lines 4262-4445 and `jsx-runtime.d.ts` line 2 (https://registry.npmjs.org/@types/react/-/react-19.3.0.tgz), checked 2026-11-12.
- The React 19 upgrade guide moves the global `JSX` namespace to `React.JSX` and shows custom tags declared by module augmentation: `declare module "react" { namespace JSX { interface IntrinsicElements { "my-element": { myElementProps: string; }; } } }`. The module to augment is `react/jsx-runtime` for `"jsx": "react-jsx"`, `react/jsx-dev-runtime` for `"react-jsxdev"`, and `react` for `"react"` and `"preserve"`. react.dev's TypeScript page has no section on custom elements. Source: https://react.dev/blog/2024/04/25/react-19-upgrade-guide#the-jsx-namespace-in-typescript and https://react.dev/learn/typescript, checked 2026-11-12.

React 19, refs, children and slots:
- A ref on a host element receives the DOM instance itself: `getPublicInstance(instance)` returns `instance`. For a custom element that is the element object. For custom elements `ref` is not written to the DOM. Source: https://github.com/facebook/react/blob/v19.3.1/packages/react-dom-bindings/src/client/ReactFiberConfigDOM.js#L420-L422 and https://github.com/facebook/react/blob/v19.3.1/packages/react-dom-bindings/src/client/ReactDOMComponent.js#L1083-L1089, checked 2026-11-12.
- String or number `children` of a custom element are set as its text; other children are rendered as DOM children of the element (its light DOM). React's test "should allow named slot projection on both web components and regular DOM elements" renders `<my-component><my-second-component slot="first" /><button slot="second">Hello</button></my-component>` and finds `slot="first"` and `slot="second"` on the light DOM children. Source: https://github.com/facebook/react/blob/v19.3.1/packages/react-dom-bindings/src/client/ReactDOMComponent.js#L1040-L1050 and https://github.com/facebook/react/blob/v19.3.1/packages/react-dom/src/__tests__/ReactDOMComponent-test.js#L418-L435, checked 2026-11-12.
- "Grouping elements in `Fragment` has no effect on the resulting DOM", so a Fragment adds no element between a slotted child and its host. Source: https://react.dev/reference/react/Fragment, checked 2026-11-12.

Spectrum Web Components:

For each SWC package it writes one `@swc-react/<name>` package (same version as the SWC package) whose `index.ts` holds one `createComponent` from `@lit/react` per custom element of the package, events collected up the superclass chain, a `<Name>Type` type export per element, and a `next.js` entry that loads each wrapper with `next/dynamic` and `ssr: false`. Disagreements between sources:
- Web Awesome's docs say React 19 needs no wrappers and call the wrappers legacy, while its build still generates and ships them for every component; lit.dev's React page still says "React is working on fixes to these issues" without naming React 19, which (per the React findings above) assigns properties and listens to custom events. Source: https://github.com/shoelace-style/webawesome/blob/1828b3992c6fee46182150422fdf4945e6521012/packages/webawesome/docs/docs/frameworks/react.md#L28 and https://lit.dev/docs/frameworks/react/, checked 2026-11-12.
- Fluent UI's Microsoft Learn React page (2021) describes hand-written `@microsoft/fast-react-wrapper` wrappers over registration functions and says React writes every prop as an attribute; the current 3.2.1 package has neither those registration functions nor any wrapper guidance, and React 19's source assigns properties for names found on the element. Source: https://learn.microsoft.com/en-us/fluent-ui/web-components/integrations/react, last-modified: 2021-10-31, and https://github.com/microsoft/fluentui/blob/f9720c35ba893c9630f4c0389d07dc6d6fd6068d/packages/web-components/docs/web-components.api.md, checked 2026-11-12.
- Event-prop naming differs between generators over the same `@lit/react` call: Lit's generator and Stencil use `on` + PascalCase or camelCase of the event name, Web Awesome and Shoelace `on` + PascalCase including the `wa-` or `sl-` prefix, and Spectrum the camelCased name without `on`. Source: the Lit, Stencil, Web Awesome and Spectrum findings above, checked 2026-11-12.
