# RES-031: What TanStack Devtools offers for extension and a fork, and which other devtools bases exist

## Question
What does TanStack Devtools offer for extension and for a fork, and which other bases for devtools exist?

## Answer
Answered. The sweep of 2026-11-12 established the first half of the question: the plugin API of TanStack Devtools, how a custom panel is added, its framework adapters, its license, its release status and versions, and what a fork must maintain. A single research agent then answered question 1 of "Next action" on 2026-11-12: the five other in-page bases Storybook, Vue DevTools, Nuxt DevTools, the Astro dev toolbar and the Vercel toolbar; see "Question 1: the other in-page bases". Every part of the sufficient-answer condition now has confirmed findings.

### What the run established
The summary of the run's report, in its own words:

> Every verified claim covers part (1), TanStack Devtools. No claim about the other bases in part (2) passed verification, so this report does not answer that part. TanStack Devtools (github.com/TanStack/devtools, MIT license) calls itself a framework-agnostic devtools panel. The panel hosts TanStack's own library devtools and custom plugins. On 2026-10-29 the core package @tanstack/devtools was at 0.16.0, and the docs label the project alpha with an API subject to change. A custom panel is a plugin object in the plugins array of the devtools component, with the fields name, render, an optional id and an optional defaultOpen. Data moves through a typed, framework-agnostic EventClient from @tanstack/devtools-event-client. With the Vite plugin, that client can bridge to a server bus. The shell and its shared UI library are written in Solid.js, so a fork of the shell would maintain Solid.js code. The repository holds adapter packages for React, Preact, Solid, Vue, Svelte and Angular. No Lit or web-component adapter appears in the repository, and TanStack Table's devtools page says Lit has no dedicated table devtools adapter. No verified claim says the TanStack sources describe live property editing or theming and design-token controls.

### Question 2: devtools for web components, TanStack as a framework-agnostic base, and Devframe
Answered by the single-agent run of 2026-11-12. The facts are in "Findings" under that run's line; the capability rows are in the table under "Question 1". Nothing here ranks the bases or recommends one.

Devtools for web components and Lit:

- Web Component DevTools (Matsuuu/web-component-devtools, MIT): a browser extension for Chrome and Firefox. v1 lists custom elements, edits their attributes and properties, observes events, and its source tree names a Custom Elements Manifest analyzer integration. Its last release is v0.1.15 of 2022-05-09. A full rewrite (main branch at 0.3.0, built with Lit and Web Awesome) has been under way since 2025-10-22; its last commit was on 2025-12-06.
- Lit Prism 1.3.0 (Chrome Web Store, 2026-06-28; MIT by its store page; no source repository is linked there): a sidebar in Chrome's Elements panel that shows and edits the reactive properties of the selected element, for Lit 1 to 3, Polymer and other custom elements.
- Lit DevTools (oddcelot/lit-devtools; @oddsquad/lit-devtools and @oddsquad/vite-plugin-lit 0.27.0, 2026-10-30, BSD-3-Clause; independent of the Lit project): a toolkit for Lit. Its panel shows the Lit elements of the page, edits primitive properties on the live element, records a timeline of events, and reads each package's Custom Elements Manifest. The panel runs as a dock in Vite DevTools, as its own page at `/__lit/` of a Vite dev server, or through a Devframe handler in a server that is not Vite. Its Lit Inspector extension for Chrome and Firefox inspects any page, production builds included. It covers Lit elements only, and it is not a framework-neutral base.
- api-viewer-element 1.0.0-pre.10 (open-wc, MIT, 2024-04-05; the last commit that is not a dependency bump was on 2024-05-17): custom elements (`<api-viewer>`, `<api-docs>`, `<api-demo>`) that read a manifest and render API documentation and a live demo with knobs, CSS custom property controls and an event log. They work on their own demo instance, not on a component selected in an app. A page can hold them like any custom element.
- WC Toolkit Storybook Helpers 10.7.7 (MIT, 2026-08-18): helpers that turn a manifest into Storybook controls for properties and CSS custom properties; they need Storybook 10.1.11 or later, below 11.
- The Custom Elements Manifest itself is a file format (schema 2.1.0, webcomponents/custom-elements-manifest, BSD-3-Clause) with a `customElements` field in package.json that tools use to find it; @custom-elements-manifest/analyzer 0.11.0 (MIT, 2025-11-04) generates it. It is a data source, not a devtools UI. The Lit project ships no devtools package; its monorepo holds @lit-labs/analyzer and @lit-labs/gen-manifest.

Whether each can be a base or a part of an in-page devtools package:

- The browser extensions (Web Component DevTools, Lit Prism, Lit Inspector) run in the browser's devtools, not in the page. No source documents reuse of their code inside a page; that reuse is UNVERIFIED.
- api-viewer-element is a set of custom elements that a page can load, so it can sit in a page; no source documents its use inside a devtools panel.

TanStack Devtools as a framework-agnostic base, the three points of "Still open":

- A panel as plain DOM code: settled yes. The core plugin contract is `render: (el: HTMLDivElement, props) => void`, and the plugin-lifecycle page says a plugin can render "raw DOM manipulation, a framework portal, or anything else" and "anything into it - DOM nodes, a framework component tree via portals, a canvas, an iframe". A custom element is a DOM node, but no TanStack source names custom elements or web components; the step from DOM nodes to custom elements is an inference.
- The shell on a plain HTML page with no framework: the docs say the core package works "with any framework or without a framework", and the core class `TanStackDevtoolsCore` has `mount(el)`, `unmount()` and `setConfig()`. With no build step: no TanStack source covers it. The published core imports the bare modules `solid-js`, `solid-js/web` and `@tanstack/devtools-event-bus/client`, so a page without a build would need an import map or a CDN that resolves them (UNVERIFIED that this works). The production page says a project without Vite must keep the devtools out of production itself.
- Live editing of properties, or controls for themes and tokens: no TanStack source describes either as a feature. The bidirectional-communication page says that two-way EventClient messages "enable features like state editing, action replay, and time-travel debugging", as a pattern for plugin authors. The only theme in the sources is the shell's own light and dark setting, passed to panels as `theme`; the architecture page calls the shared semantic theme internal, "not a public theming API for application plugins".
- New since the sweep: TanStack ships an accessibility plugin, @tanstack/devtools-a11y 0.2.3 (MIT, 2026-10-29), with axe-core, rule presets from WCAG 2.0 A to WCAG 2.2 AA, page overlays, and Export JSON and Export CSV downloads. Its panel is written in Solid.

The Vite DevTools Kit and Devframe:

- The Vite DevTools Kit (@vitejs/devtools-kit 0.8.2, MIT, VoidZero; 72 versions published in 2026) is the hub of Vite DevTools: dock, command palette, terminals, messages, RPC and shared state, entered through a Vite plugin's `devtools.setup` hook. It needs Vite 8.3 or later. Its docs give no way to host it in an app that does not use Vite; they send "standalone single-tool deployments" to Devframe.
- Devframe (devframe 1.3.3, MIT, Anthony Fu; first published 2026-04-23, 91 versions in 2026) is "a framework-neutral foundation for devtools". One definition becomes a Web Standard request handler for any server (Hono, Nitro, Next.js, SvelteKit; Vite and Rsbuild through middleware), a CLI, a static build, or an MCP server. Its in-page channel links a page script and its panels in the browser with no server. A devframe still needs a JavaScript server process for its handler and RPC; a plain HTML page with no server and no build step is not a documented host. Lit DevTools runs on Devframe in a server that is not Vite (Elysia in its example).

## Findings
- Plugin architecture: a custom plugin has two parts. The first is an EventClient from @tanstack/devtools-event-client. It is a typed, framework-agnostic event emitter and listener, subclassed with a pluginId and an event map, and it carries data between the app and the devtools. The second is a panel component that renders in the devtools UI. Same-page communication needs no server. A panel written in the adapter's framework makes the plugin specific to that framework. One React guide says the framework-agnostic panel approach will be explained in 'coming docs'. Evidence: Docs, read 2026-11-12: 'A plugin consists of two parts: 1. An EventClient ... 2. A panel component ... The EventClient is framework-agnostic.' 'It is built on EventClient, a type-safe event emitter/listener from @tanstack/devtools-event-client. It is completely framework-agnostic.' The React guide adds: 'write the devtools in the framework that the adapter is, be aware that this will make the plugin framework specific.' The same site lists 'Building Custom Plugins', 'Using devtools-utils' and 'Bidirectional Communication' guides, which may cover the deferred approach. The verifiers did not open them to confirm. Confidence high; vote 3-0 on all merged claims ([0],[7],[9],[18]). Source: https://tanstack.com/devtools/latest/docs/building-custom-plugins and https://tanstack.com/devtools/latest/docs/framework/react/guides/custom-plugins and https://tanstack.com/devtools/latest/docs/event-system, checked 2026-11-12.
- Adding a custom panel: a plugin object goes in the plugins array prop of the devtools component, and each object is one sidebar tab. React adapter type: { id?: string; name: string | PluginRender; render: PluginRender; defaultOpen?: boolean }. name is the tab title. If id is omitted, it is generated from name. defaultOpen opens the panel on first load. render takes a JSX element (React, Preact) or a component reference (Vue, Solid). In React, render can also be a function (el: HTMLElement, { theme, devtoolsOpen }) => JSX.Element, which gives raw DOM access to the container. Evidence: React adapter page: 'Each plugin describes a tab in the devtools panel' and 'render can be a JSX element ... or a function that receives the container element and current { theme, devtoolsOpen } props.' The custom-plugins page: 'The render field accepts a JSX element (React, Preact) or a component reference (Vue, Solid), depending on your adapter.' Devframe:
- Devframe calls itself "a framework-neutral foundation for building a devtool once and running it everywhere - inside any host framework, as a standalone tool, or through a coding agent"; its handler serves the web interface, connection metadata, live RPC, authentication and an optional MCP endpoint, and "Hono and Nitro take Web Standard requests directly; Next.js and SvelteKit expose route handlers; Vite and Rsbuild accept its nodeMiddleware". Source: https://github.com/devframes/devframe/blob/818c941bf6d27136234c1578d9e05b3d408c12ef/docs/content/1.guide/index.md (lines 8-59), checked 2026-11-12.
- Its entry points are the standard handler `initDevframe(def, { base })`, and the adapters cac (CLI), dev (dev server), build (static snapshot), vite (through @vitejs/devtools-kit's createPluginFromDevframe), embedded (registration into a running context) and mcp. Source: https://github.com/devframes/devframe/blob/818c941bf6d27136234c1578d9e05b3d408c12ef/docs/content/2.adapters/index.md, checked 2026-11-12.
- The in-page channel connects a devframe's page script to its panels "entirely in the browser: typed events, calls, and page-script-authoritative shared state, with no server involved", through a same-origin postMessage handshake and a MessageChannel port.
