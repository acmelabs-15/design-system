# RES-072: How the React reference systems compose components from parts

## Question
How do shadcn/ui, Radix Primitives, Radix Themes and Geist let a developer compose a component from its parts: which parts does each export, does a component that composes the subcomponents exist beside them and where does it live, how do the parts share state, and how does a developer wrap or replace a part? Which names do these systems, React's documentation and wider React writing give to this pattern and to its two forms, and what do they state as best practice for it?

Settled context: the core of the new design system is Lit web components, and framework packages (React first) wrap the core. Each framework package must export every subcomponent of a component, and also a ready-made component that composes them. DEC-148: a glossary term takes the standard name of its pattern, found by research. DEC-149: a user of each framework must not be surprised at how the components are built. RES-042 holds the same facts for Chakra UI 3 and is not repeated here.

Needed by: IDEA-003#05 (the composition architecture of the Lit core) and IDEA-003#06 (where the ready-made component lives, and the glossary terms).

## Answer
Sufficient-answer condition: for each of the four systems, at its current named version, from its documentation and its source code: (1) the export shape on two or three components with parts, one with state; (2) whether a ready-made single component exists beside the parts, where it lives and who owns it; (3) how the parts share state and in which layer; (4) the documented means to wrap or replace a part, their named limits, and whether a part still works when a developer's element sits between it and its parent part; (5) the names for the pattern, the parts and the ready-made form in each system, on react.dev and in widely cited React writing, and where they disagree; (6) each statement of best practice for composition. shadcn/ui in its Radix UI and Base UI variants. Limits and contrary evidence. One short table at the end. Facts and sources only; no recommendation.

Answered on 2026-11-13. The sufficient-answer condition is met for Radix Primitives, Radix Themes and shadcn/ui from documentation and source. For Geist it is met from documentation only: no public source was found (the package is not on the public npm registry, and two likely GitHub repositories answer 404). The brief foresaw that limit.

Versions: Radix Primitives `radix-ui` 1.8.1 (source commit eb3a2b7, 2026-10-14). Radix Themes `@radix-ui/themes` 3.3.0 (commit 1faff10, 2026-04-11). shadcn/ui CLI `shadcn` 4.23.0 (commit e62c943, 2026-11-13), with its Radix UI base and its Base UI base; Base UI was read at `@base-ui/react` 1.9.0 (commit 315eba7), and shadcn's own docs app pins 1.6.0. Geist states no version; its docs were read on 2026-11-13.

1. **Export shape.**
   - Radix Primitives: one package for each primitive, and each part is exported under a long name and a short alias (`DialogTrigger` and `Trigger`). The unified package re-exports each primitive as a module namespace, so a developer writes `Dialog.Root`, `Dialog.Trigger`, `Tabs.List`, `Accordion.Item`. `Dialog.Root` is a namespace member, not a property on a function.
   - Radix Themes: 18 components are module namespaces with short names only (`Dialog.Root`, `Tabs.Trigger`). All other components are single named exports. Since 3.0.0 the long names are gone: "Use dot notation instead, which was revised to work with React Server Components".
   - shadcn/ui: one file for each component with flat named exports and no namespace (`Dialog`, `DialogTrigger`, `DialogContent`; `Tabs`, `TabsList`, `TabsTrigger`, `TabsContent`). The export names are the same in the Radix UI and the Base UI variant, although the parts below have different names (Radix `Overlay` and `Content` are Base UI `Backdrop` and `Popup`).
   - Geist: flat named exports from one barrel module (`Modal`, `ModalBody`, `ModalHeader`, `ModalTitle`, `ModalActions`, `ModalAction`). The prose of its pages also writes `Modal.Title` and `Combobox.Option`, which the examples do not import.
   - In all four, the name without a suffix (`Dialog`, `Tabs`, `Modal`) or `Root` is the root part. It is not a component that assembles the other parts.
2. **Ready-made single component beside the parts.** None of the four ships, for one component and in one place, both the full set of parts and a component that assembles them. One exception was found: shadcn's Base UI `progress.tsx`. What each has in its place:
   - Radix Primitives: nothing in the package. Seven docs pages have a section "Custom APIs" with an example that the developer writes and owns ("Create your own API by abstracting the primitive parts into your own component").
   - Radix Themes: a component is either parts or closed, never both. Closed single components in the package stand where the Primitive has parts: Slider, Tooltip, Checkbox, Switch, Progress, Avatar, ScrollArea. Their parts are not exported by Themes. Radix owns them. A Themes part can also hide several Primitive parts (`Dialog.Content` holds Portal, Overlay and Content).
   - shadcn/ui: the file is copied into the consumer's project, and the consumer owns it. Some parts are partly assembled (`DialogContent` holds the portal, the overlay and a close button behind `showCloseButton`). Some components are closed single exports (`Slider`, `Checkbox`, `Switch`). The Base UI `Progress` renders its track and indicator itself and also exports them as parts. For a ready-made form of a component with parts, shadcn's guide tells the developer to write a "wrapper component".
   - Geist: several components exist only as one closed component configured through props (`Tabs` with a `tabs` array, `Tooltip`, `Drawer`, `Collapse`). No page shows one component in both forms.
3. **State sharing.**
   - Radix Primitives: React context, in Radix's own `@radix-ui/react-context`. The root holds the state with `useControllableState` and provides it. Each part reads it with a hook that throws outside the root. There is no state machine and no layer below. The context hooks are not exported.
   - Radix Themes: the same context, because each Themes part wraps the Primitive part. Themes adds React context only for style values such as `size`.
   - shadcn/ui: the file holds no state for Dialog, Tabs or Accordion. The state lives in the headless layer: the React context of Radix Primitives, or of Base UI (which puts a context object, and for Dialog a store, into React context). Components that shadcn builds itself (Sidebar, Carousel, Chart) use their own React context with an exported hook.
   - Geist: not documented, and not confirmed.
   - In the three systems with public source, no parent finds its parts by reading its children. Parts that need an order register through context and are sorted by their position in the DOM.
4. **Wrap or replace a part.**
   - Radix Primitives: `asChild`, built on `Slot`. The part renders no element of its own and merges its props, handlers and ref onto its one child element. Named limits: the child must spread the props and forward the ref; exactly one child element; the developer must keep the result accessible. `Slot` is exported for the developer's own components. No public hook lets a custom part read the root's state.
   - Radix Themes: `asChild` reworked for each part. The trigger and close parts of the overlay components (Dialog, AlertDialog, Popover, HoverCard, DropdownMenu, ContextMenu) always use it and throw without a single element child. Some parts remove it (`Tabs.List`, `Tabs.Trigger`). Others keep it. Themes has no composition guide.
   - shadcn/ui, Radix UI variant: `asChild` as above. Base UI variant: the `render` prop, which takes an element (`render={<Button />}`) or a function `(props, state) => element`. Named limits: forward the ref and spread the props; add `nativeButton={false}` when the element is not a button; do not render a Button as a link. Base UI also has detached triggers through `Dialog.createHandle()`. In both variants the developer can also edit the copied file.
   - Geist: `asChild` on Sheet, a `render` prop on Context Card, and a variant prop (`type="unstyled"`) on the Menu button. No limits are named.
   - An element of the developer between a part and its parent part: it works in Radix Primitives, Radix Themes and both shadcn variants, because the part reads context at any depth. The official Themes examples do it (`Tabs.Root` > `Box` > `Tabs.Content`). Two limits apply. With `asChild` the replacing element must be the one direct child of the part. And shadcn's rules name required ancestors ("always wrap in `TabsList`", items inside their Group) and say "Don't wrap triggers in extra elements". For Geist the examples nest parts inside other parts, and nothing more is stated.
5. **Names.**
   - The pattern: "compound components" in Kent C. Dodds, patterns.dev ("compound component pattern"), Smashing Magazine and Vercel's composition guide. Chakra UI writes "open, compound components" (RES-042). The docs of the four systems do not use the word: Radix Primitives says "open component architecture", Radix Themes "multi-part components", shadcn/ui "Composition" and "composable interface", and Geist gives no name. react.dev does not use "compound components" anywhere; it writes "Exposing multiple components". Base UI has "Compound Components" only as a page keyword.
   - The parts: "parts" (Radix Primitives, Radix Themes, Base UI), "subcomponents" (shadcn/ui, Vercel's guide), "child components" (patterns.dev, Smashing Magazine). The list of parts is "Anatomy" in Radix Primitives and Base UI and "Composition" in shadcn/ui. The first part is `Root` in Radix and Base UI.
   - The ready-made form: no shared name. "Custom APIs", made by "abstracting the primitive parts into your own component" (Radix Primitives). "Wrapper components" (shadcn/ui). "Explicit variants" (Vercel's guide). "Closed components" (Chakra UI, RES-042). "Specialization" (the older React docs: a more specific component renders a more generic one and configures it with props). Radix Themes and Geist ship such components and give them no name.
   - The form configured through props has two more names: "Accepting an array of objects as a prop" (react.dev) and "monolithic component" (Vercel's guide, as the thing to avoid).
   - Dot notation means two things. patterns.dev and Smashing Magazine set the parts as properties on the parent function (`FlyOut.Toggle = Toggle`). Radix and Base UI export a module namespace. Kent C. Dodds' example, shadcn/ui and Geist use flat names.
6. **Best practice stated by the sources.**
   - react.dev: reading or cloning children "is uncommon and can lead to fragile code"; pass data through a render prop or through context, or expose multiple components. Do not overuse context: try props and `children` first. `forwardRef` is no longer needed in React 19.
   - Radix Primitives: always spread props and forward the ref in a leaf component. Keep the default element in most cases. Compose triggers with the design system's own buttons and links.
   - Base UI: the same two rules for `render`; render another element "only on a case-by-case basis".
   - shadcn/ui: "Use full composition"; keep the documented tree (trigger inside list, items inside group, a title in every dialog); prefer variants, then `className`, then a new variant, then a wrapper component.
   - Vercel's guide: compound components with a shared context; no boolean props for behaviour; explicit variants; `children` over render props, except when the parent passes data to the child.
   - patterns.dev and Smashing Magazine: the `cloneElement` implementation reaches direct children only; context removes that limit.
   - Geist's docs state no general rule on composition.

Limits and contrary evidence:
- The Base UI facts come from 1.9.0, and shadcn's docs app pins 1.6.0. shadcn's React Aria base was not read.
- Radix Primitives' guide still requires `React.forwardRef`, which react.dev marks as due for deprecation.
- Vercel's composition guide is not part of the Geist docs. Geist's `Tabs` with a `tabs` array is the prop-configured form that the guide argues against for complex components.
- shadcn says of its two variants: "The components look and behave the same way." Its later migration notes speak of "every rename, every prop change, every behavior difference" between them.
- Issue trackers were not searched for further limits of `asChild` or `render`.

## Findings

Capability check, 2026-11-13: loaded brain:source-driven-development. Web tool: Firecrawl scrape answered with HTTP 200 on https://www.radix-ui.com/primitives/docs/guides/composition. Source was read from shallow clones of github.com/radix-ui/primitives (commit eb3a2b7091293e27df8f9ba906632d8daa3d81a3, 2026-10-14), github.com/radix-ui/website (commit 402e749613ab2e7ab7139c65b0029842b0360f07, 2026-10-07), github.com/radix-ui/themes (commit 1faff10ac26ae17f09944d418c6949b93fc6b566, 2026-04-11), github.com/shadcn-ui/ui (commit e62c9435fff729a175f38983dee73b2cb4f6a069, 2026-11-13) and github.com/mui/base-ui (commit 315eba7a3d8a0a53d47fe7b902cb75daa21f6814, 2026-11-13).

Radix Primitives:

- The unified package `radix-ui` is version 1.8.1. At that commit `@radix-ui/react-dialog` is 1.3.1, `@radix-ui/react-tabs` 1.2.1, `@radix-ui/react-accordion` 1.3.1, `@radix-ui/react-slot` 1.5.0 and `@radix-ui/react-context` 1.3.0. Source: https://github.com/radix-ui/primitives/blob/eb3a2b7091293e27df8f9ba906632d8daa3d81a3/packages/react/radix-ui/package.json and the `package.json` of each named package under packages/react at that commit, checked 2026-11-13.
- `radix-ui` re-exports each primitive package as an ES module namespace: `export * as Dialog from '@radix-ui/react-dialog'`, and the same for Tabs, Accordion and the others. Source: https://github.com/radix-ui/primitives/blob/eb3a2b7091293e27df8f9ba906632d8daa3d81a3/packages/react/radix-ui/src/index.ts, checked 2026-11-13.
- Each primitive package exports every part twice: under a long name (`Dialog`, `DialogTrigger`, `DialogPortal`, `DialogOverlay`, `DialogContent`, `DialogTitle`, `DialogDescription`, `DialogClose`) and under a short alias (`Root`, `Trigger`, `Portal`, `Overlay`, `Content`, `Title`, `Description`, `Close`). Tabs exports `Tabs`, `TabsList`, `TabsTrigger`, `TabsContent` and `Root`, `List`, `Trigger`, `Content`. Accordion exports `Accordion`, `AccordionItem`, `AccordionHeader`, `AccordionTrigger`, `AccordionContent` and `Root`, `Item`, `Header`, `Trigger`, `Content`. So `Dialog.Root` is a member of a module namespace, not a property set on a function. The long name `Dialog` is the root part only. It renders no other part. Source: packages/react/dialog/src/index.ts, packages/react/tabs/src/index.ts and packages/react/accordion/src/index.ts at the commit above, checked 2026-11-13.
- The package has no ready-made component that assembles the parts. Each docs page shows the parts under "Anatomy" with this sentence: "Import all parts and piece them together". Source: https://www.radix-ui.com/primitives/docs/components/tabs#anatomy (file data/primitives/docs/components/tabs.mdx:30-45 in radix-ui/website at 402e749), checked 2026-11-13.
- The ready-made form is a documentation example that the developer writes and owns. Seven component pages (Dialog, Tooltip, Popover, Slider, Select, Dropdown Menu, Toast) have a section "Custom APIs" with the sentence "Create your own API by abstracting the primitive parts into your own component." The Slider example "abstracts all of the `Slider` parts so it can be used as a self closing element" (`<Slider defaultValue={[25]} />`). The Tooltip example "abstracts all of the `Tooltip` parts and introduces a new `content` prop". The Dialog example abstracts only `Dialog.Overlay` and `Dialog.Close` into a `DialogContent`, and re-exports `Root` and `Trigger` unchanged. Source: https://www.radix-ui.com/primitives/docs/components/dialog#custom-apis, https://www.radix-ui.com/primitives/docs/components/slider#custom-apis, https://www.radix-ui.com/primitives/docs/components/tooltip#custom-apis (files dialog.mdx:541-580, slider.mdx:554-585, tooltip.mdx:667-710 at 402e749), checked 2026-11-13.
- The parts share state through React context, in Radix's own package `@radix-ui/react-context`. There is no state machine and no separate headless layer below. `Tabs` (root) holds the value with `useControllableState` and renders `TabsProvider` with `baseId`, `value`, `onValueChange`, `orientation`, `dir` and `activationMode`. `TabsList`, `TabsTrigger` and `TabsContent` each call `useTabsContext(...)`. A trigger and its content are matched by the `value` prop of each, and their ids are derived from `baseId` and `value`. Source: https://github.com/radix-ui/primitives/blob/eb3a2b7091293e27df8f9ba906632d8daa3d81a3/packages/react/tabs/src/tabs.tsx (lines 28-42, 71-111, 124-147, 161-230, 249-297), checked 2026-11-13.
- The context helper creates a `React.createContext` and a `useContext` hook that throws when the part is outside its root: "`<part>` must be used within `<root>`". `createContextScope` adds scopes, so that one primitive can be built from another (Tabs from RovingFocusGroup) without their contexts colliding. Source: https://github.com/radix-ui/primitives/blob/eb3a2b7091293e27df8f9ba906632d8daa3d81a3/packages/react/context/src/create-context.tsx (lines 26-63, 106-183), checked 2026-11-13.
- Dialog's root is a function component with no DOM element. It holds `open` with `useControllableState` and provides `triggerRef`, `contentRef`, `contentId`, `titleId`, the description ids and `open` handlers through `DialogProvider`. Every other part reads `useDialogContext`. Source: packages/react/dialog/src/dialog.tsx:33-130 at the commit above, checked 2026-11-13.
- A part works at any depth below its root, because it reads React context and not its parent's children. Parts that need an order (roving focus in Tabs, arrow keys in Accordion) register through a collection context. The collection finds the order from the DOM: the legacy collection queries the collection node for `[data-radix-collection-item]` (`querySelectorAll`, so any depth), and the new collection sorts by document position. Source: packages/react/collection/src/collection-legacy.tsx:86-128 and packages/react/collection/src/collection.tsx:36-45, 121-132 at the commit above, checked 2026-11-13.
- The context hooks of a primitive are not exported. `@radix-ui/react-dialog` exports the parts, their types and `createDialogScope`, and no `useDialogContext`. So a developer's own component cannot read the root's state through a public hook. It reads state from the controlled props (`open`, `onOpenChange`) or from the `data-state` attributes. Source: packages/react/dialog/src/index.ts at the commit above, checked 2026-11-13.
- The documented means to wrap or replace a part is `asChild`: "All Radix primitive parts that render a DOM element accept an `asChild` prop. When `asChild` is set to `true`, Radix will not render a default DOM element, instead cloning the part's child and passing it the props and behavior required to make it functional." Named limits: "Your component must spread props" and "Your component must forward ref"; when the element type changes, "it is your responsibility to ensure it remains accessible and functional". "`asChild` can be used as deeply as you need to", which composes two primitives on one element (`Tooltip.Trigger asChild` > `Dialog.Trigger asChild` > `MyButton`). Source: https://www.radix-ui.com/primitives/docs/guides/composition, checked 2026-11-13.
- `asChild` is implemented in `Primitive`: `const Comp = asChild ? Slot : node`. `Slot` clones its single child element with merged props. Event handlers of both are composed (the child's runs first), `style` is merged, `className` is joined, `aria-describedby` is concatenated, and the child's other props win. It throws when the children are not one element. `Slottable` marks which child takes the props when a component has several children. Source: packages/react/primitive/src/primitive.tsx:44-60 and packages/react/slot/src/slot.tsx:20-93, 114-178 at the commit above, checked 2026-11-13.
- `Slot` is exported as a utility for the developer's own components: "Can be used to support your own `asChild` prop". Source: https://www.radix-ui.com/primitives/docs/utilities/slot, checked 2026-11-13.
- Names in the Radix Primitives docs: "parts" and "component part" for the subcomponents; "Anatomy" for the section that lists them; "open component architecture" for the pattern ("Our open component architecture provides you granular access to each component part, so you can wrap them and add your own event listeners, props, or refs", under the key feature "Opened"); "Custom APIs" and "abstracting the primitive parts into your own component" for the ready-made form. The words "compound" and "closed component" do not occur in the docs folder. Source: https://www.radix-ui.com/primitives/docs/overview/introduction and a grep of data/primitives/docs in radix-ui/website at 402e749, checked 2026-11-13.
- Best practice stated by the Radix Primitives docs: on spreading props, "We recommend always doing this so that you are not concerned with implementation details ... We find this is good practice for "leaf" components in general"; on forwarding the ref, "we recommend always doing it"; "In the majority of cases you shouldn't need to modify the element type as Radix has been designed to provide the most appropriate defaults"; "it's more common to use your own React components. This is especially true for most `Trigger` parts, as you usually want to compose the functionality with the custom buttons and links in your design system". Source: https://www.radix-ui.com/primitives/docs/guides/composition, checked 2026-11-13.

Radix Themes:

- `@radix-ui/themes` is version 3.3.0 at that commit, and depends on `radix-ui` ^1.1.3 (the Primitives). The Releases page of the documentation lists 3.1.3 as its newest entry (RES-034 holds the same gap). Source: https://github.com/radix-ui/themes/blob/1faff10ac26ae17f09944d418c6949b93fc6b566/packages/radix-ui-themes/package.json and https://www.radix-ui.com/themes/docs/overview/releases, checked 2026-11-13.
- The package exports each component in one of two shapes, never in both. 18 components are namespaces of parts (`export * as Dialog from './dialog.js'`): AlertDialog, Callout, CheckboxCards, CheckboxGroup, ContextMenu, DataList, Dialog, DropdownMenu, HoverCard, Popover, RadioCards, RadioGroup, SegmentedControl, Select, TabNav, Table, Tabs, TextField. The others are single named components (`export { Slider }`, `export { Tooltip }`, `export { Checkbox }`, `export { Button }`). Source: https://github.com/radix-ui/themes/blob/1faff10ac26ae17f09944d418c6949b93fc6b566/packages/radix-ui-themes/src/components/index.tsx, checked 2026-11-13.
- A namespaced component exports only short names: `tabs.tsx` exports `TabsRoot as Root`, `TabsList as List`, `TabsTrigger as Trigger`, `TabsContent as Content`; `dialog.tsx` exports `Root`, `Trigger`, `Content`, `Title`, `Description`, `Close`. There is no long name such as `DialogRoot` on the package. The 3.0.0 upgrade guide says: "Multi-part components now don't export named parts anymore. Use dot notation instead, which was revised to work with React Server Components", for example "`DialogRoot` → `Dialog.Root`". Source: packages/radix-ui-themes/src/components/tabs.tsx:100-106 and dialog.tsx:108-124 at the commit above; https://www.radix-ui.com/themes/docs/overview/releases (section 3.0.0, "Upgrade guide", file data/themes/docs/overview/releases.mdx:85-96 in radix-ui/website at 402e749), checked 2026-11-13.
- The ready-made form exists in the package, but only as the sole shape of a component, not beside its parts. Themes ships a closed single component where the Primitive has parts: `Slider` renders `SliderPrimitive.Root`, `Track`, `Range` and one `Thumb` for each value, and removes `children` from its props; `Tooltip` renders `Root`, `Trigger asChild`, `Portal`, `Content` and `Arrow` from a `content` prop; `Checkbox` (Root + Indicator), `Switch` (Root + Thumb), `Progress` (Root + Indicator), `Avatar` (Root + Image + Fallback) and `ScrollArea` (Root + Viewport + Scrollbar + Thumb + Corner) are closed in the same way. The parts of these components are not exported by Themes. A developer who needs them imports the Primitive. Source: packages/radix-ui-themes/src/components/slider.tsx:13-57, tooltip.tsx:13-64 and a grep of `Primitive.<Part>` in checkbox.tsx, switch.tsx, progress.tsx, avatar.tsx and scroll-area.tsx at the commit above, checked 2026-11-13.
- A Themes part can itself hide several Primitive parts. `Dialog.Content` renders `DialogPrimitive.Portal`, `Theme asChild`, `DialogPrimitive.Overlay`, two scroll `div`s and `DialogPrimitive.Content`. So Themes' Dialog has 6 parts (Root, Trigger, Content, Title, Description, Close), and the Primitive's Dialog has 8 (it adds Portal and Overlay). Source: packages/radix-ui-themes/src/components/dialog.tsx:44-70 at the commit above, checked 2026-11-13.
- Themes adds no behavioural state. Each part wraps the matching Primitive part, so the parts share state through the Primitive's React context. Themes adds its own React context only for style values that a root hands to its parts: `SelectContext` (`size`), `CalloutContext` (`size`), `DropdownMenuContentContext` and `ContextMenuContentContext` (`size`, `variant`, `color`, `highContrast`), and scoped contexts in RadioGroup, CheckboxGroup and CheckboxCards. Source: packages/radix-ui-themes/src/components/select.tsx:20-36, 45-55, and a grep of `createContext` in the components directory at the commit above, checked 2026-11-13.
- Themes reworks `asChild` for each part, and its docs have no composition guide. Three cases are in the source. (a) Trigger parts force it: `Dialog.Trigger` and `Dialog.Close` always pass `asChild` to the Primitive and call `requireReactElement(children)`, which throws "Expected a single React Element child" for anything else. So the developer always supplies the button. The same call is in alert-dialog.tsx, popover.tsx, hover-card.tsx, dropdown-menu.tsx and context-menu.tsx. (b) Some parts remove it: `RemovedProps` is `'asChild' | 'defaultChecked' | 'defaultValue' | 'color'`, and `Tabs.List` and `Tabs.Trigger` pass `asChild={false}` to the Primitive.
