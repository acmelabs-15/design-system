# RES-081: Design systems that export granular parts and out-of-the-box components from one package

## Question
Which of the more popular design systems and component libraries export, from one package, both the granular composable parts of a component and an out-of-the-box component for the same concept, which is one component or a much simpler composition? What do they call each of the two, and which name do documentation and widely cited writing give to this pattern?

Peter asked for this research on 2026-11-20, with `/deep-research`, in his reply to IDEA-003#06. He doubts the statement that no system ships both from one package. That statement rests on RES-072 and RES-069, which cover the five reference systems and thirteen libraries of web components only.

Needed by: IDEA-003#06, where the out-of-the-box component lives; IDEA-003#24, the names for the glossary (DEC-148); IDEA-001#09, the review of the parts.

## Answer
Answered on 2026-11-20, from two runs. The second run surveyed 38 subjects: 37 design systems and component libraries, and one subject for the writing on the pattern. A second agent checked each record against the sources and corrected 36 of the 38.

Peter's doubt is right. The statement that no system ships both ways from one package holds only for the sets of RES-072 and RES-069.

- 24 of 37 systems offer at least one component concept both ways from one package: Mantine, IBM Carbon React, IBM Carbon Web Components, Ant Design, MUI Material UI, Atlassian Design System (Atlaskit), Shopify Polaris (React and Polaris web components), GitHub Primer React, PrimeVue, Adobe React Spectrum (Spectrum 2, @react-spectrum/s2), HeroUI (version 3), Vuetify, Element Plus, Naive UI, Quasar, React Bootstrap, Blueprint (Palantir), Base Web (Uber), Arco Design, Salesforce Lightning base components, Semantic UI React, NG-ZORRO (ng-zorro-antd, Ant Design for Angular), Ant Design Vue, Web Awesome (successor of Shoelace).
- 2 offer both ways from two packages: Reka UI and Nuxt UI, Angular Material and the Angular CDK.
- 6 offer parts only: Base UI (base-ui.com), Microsoft Fluent UI Web Components, PrimeReact, Adobe React Aria Components, Headless UI, Kobalte.
- 5 chose "differs by component": Microsoft Fluent UI React v9, Ark UI and Park UI, Gestalt (Pinterest), Flowbite React, Tremor.
- No system offers out-of-the-box components only.

How far the pattern goes differs much between systems, and in each system it differs by component.
- Wide, and built on the exported parts: Mantine (nine concepts; `Modal` beside `Modal.Root` and the other parts on one export; `Select` beside `Combobox`), MUI (`TextField` beside `FormControl`, `InputLabel` and the inputs), Vuetify, Element Plus, Naive UI, Arco Design, Blueprint, Semantic UI React, Spectrum 2, and Park UI with its "Shortcuts".
- One or a few concepts only: Carbon React (the modal, and `Modal` is not built on the parts), Atlassian (Popup), Polaris React (Autocomplete beside Combobox and Listbox), Fluent UI React 9 (DataGrid beside the Table primitives), Web Awesome (Toast only) and HeroUI 3 (Toast only).
- In Ant Design the direction is the other way: the data prop, such as `items`, is the main way, and the child components are deprecated.
- Two systems moved to parts and deprecate their single components: PrimeVue 5 and PrimeReact 11. HeroUI 3 did the same.
- Libraries of web components: the pattern is rare. Web Awesome has it for Toast, Carbon Web Components for about four concepts, and Fluent UI Web Components and the Polaris web components are parts only. This agrees with RES-069, with these cases added.

The name of the pattern: no source gives one standard name.
- For the granular way the most used term is "compound components". Others: "subcomponents", "parts", "primitives", "composable components".
- For the out-of-the-box way each system has its own word: "closed component", "shorthand props", "convenience wrapper", "convenience component", "wrapper component", "preset", "shortcuts", "config components", "builder components".
- For the two ways together, in the writing that developers cite: "layered components" and "layering component APIs" (Alan B. Smith); "progressive disclosure of complexity" (Jason Lengstorf; also Smith, Mae Capozzi and HeroUI); "Primitives and Core" (Mae Capozzi); "from (just) configuration to (also) composition" and "offer composable subcomponents, too" (Nathan Curtis); and, in one system, the "spectrum of abstraction" with its "layer model" (GitHub Primer).

Which way is the default: the out-of-the-box way is first or recommended in Mantine, MUI, Vuetify, Blueprint, Salesforce and Ant Design, among others. The granular way is first in PrimeVue, Element Plus, Naive UI, Spectrum 2, Park UI and Carbon Web Components. The list is under "Terms, defaults and disagreements".

Limits: the value for "both ways" was applied unevenly by the agents; some chose "both from one package" for one concept and some chose "differs by component" for the same state. So the count of 24 means "at least one concept", and the lines of each system hold the true extent. The source code was read for most systems that have both ways; the points that stayed open are at the end.

### Terms, defaults and disagreements
Terms that the records quote, with who uses each:
- "spectrum of abstraction / layer model": GitHub Primer React (style.md; ADR-024, which is Proposed).
- "Config components / Presentational components": GitHub Primer React.
- "closed component": Park UI docs; Ark UI archived v3 guide 'Closed Components'.
- "shortcuts": Park UI.
- "Layered Components / layering component APIs": Alan B. Smith (in the writing record).

- "Builder Components / Composable Components": Alan B. Smith.
- "configurable / composable": Nathan Curtis.
- "three-layer stack": Vuetify0 1.0 announcement (John Leider).
- "recomposition": Fluent UI React v9 contributor docs (the general practice).
- "higher level extension": Fluent UI React v9 (DataGrid).
- "compound components / compound component pattern": Mantine, HeroUI, PrimeReact, PrimeVue ('compound API'), Carbon React Tearsheet, Flowbite (deprecated form), Kent C. Dodds; names only the granular way.
- "shorthand props": Mantine (EmptyState); Semantic UI React ('Shorthand Props' beside 'Sub Components').
- "convenience wrapper": Shopify Polaris React (Autocomplete).
- "convenience component / higher-level component": React Bootstrap.
- "preset": Naive UI.
- "Shortcut": Element Plus (options attribute).

- Mantine (@mantine/core) exports both ways from one package and on one export. The ready-made Modal is configured by props: opened, onClose, title, centered, size, fullScreen, withCloseButton, overlayProps, transitionProps and closeButtonProps. The same Modal export carries the granular parts Modal.Root, Modal.Overlay, Modal.Content, Modal.Header, Modal.Title, Modal.CloseButton and Modal.Body. The docs call the parts 'compound components' and say to use them 'to have full control over the Modal rendering'. The props-configured Modal appears first in the Usage section and in almost every example, so it is the de facto default, although the docs never use the word 'default'. The docs also say that Modal.Stack works only with Modal, not with components built from Modal.Root. Evidence: Claims 0 and 1, both voted 3-0 on the primary docs as scraped on 2026-11-20. Quote: 'You can use the following compound components to have full control over the `Modal` rendering: `Modal.Root` – context provider ...'. The page does not state that the simple Modal is built internally on these parts. The Mantine version shown was not recorded. Confidence high; vote 3-0. Source: https://mantine.dev/core/modal/, checked 2026-11-20.
- Carbon React (@carbon/react) exports both ways from one package, as two sibling components. Modal is configured by props such as modalHeading, primaryButtonText, secondaryButtonText, passiveModal and danger. ComposedModal is composed from ModalHeader, ModalBody and ModalFooter. The docs call them 'both modal variants'. Searches of the two docs pages found no use of 'compound', 'primitive' or 'layered'. ComposedModal 'provides more flexibility when it comes to custom content'. The docs tie the choice to button layout. With Modal 'you have limited control over the set of buttons': a one-button modal says 'Use <ComposedModal>'. Three buttons appear only in the ComposedModal guidance, as Button children of ModalFooter, which also needs application-level CSS. The docs name neither way as the default. Evidence: Claims 2 and 3 were voted 3-0 and claim 4 was voted 2-1, all on Storybook MDX from the current main branch. The evidence does not show that Modal is built internally on ModalHeader, ModalBody and ModalFooter. The two ways are not fully equivalent, because a one-button footer is possible only with ComposedModal. Confidence high; vote 3-0 (button-layout guidance 2-1). Source: https://react.carbondesignsystem.com/?path=/docs/components-composedmodal--overview and https://github.com/carbon-design-system/carbon/blob/main/packages/react/src/components/ComposedModal/ComposedModal.mdx, checked 2026-11-20.
- Carbon Components Svelte (carbon-components-svelte) offers the same pair from one package. ComposedModal is used with ModalHeader, ModalBody and ModalFooter, and Modal is the simpler component. The docs say: 'The composed modal provides a composition-based approach ... for maximum flexibility. For simpler use cases, use Modal instead. Both components share the same events, accessibility features, and focus behavior.' This library is a Svelte port of Carbon and is not on the list of systems the question asks about. Its docs name no default and do not say that Modal is built on the parts. Evidence: Claims 9, 10 and 11, all voted 3-0, from the primary docs scraped on 2026-11-20. This is a neighboring data point only. It is not evidence about Carbon React or Carbon Web Components. Confidence high; vote 3-0. Source: https://svelte.carbondesignsystem.com/components/ComposedModal, checked 2026-11-20.
- Chakra UI v3 splits the two ways across delivery channels. @chakra-ui/react exports only the granular parts, for example Field.Root, Field.Label, Field.RequiredIndicator, Field.HelperText, Field.ErrorText and Field.ErrorIcon. This parts composition is the default in the Usage section. The out-of-the-box form is a 'closed component composition'. It is a user-owned snippet built on the same parts and configured by the props label, helperText, errorText and optionalText. It is copied by hand or added with 'npx @chakra-ui/cli snippet add field'. It is not a package export. The migration guide says: 'Snippets provide pre-built compositions of Chakra components to save you time and put you in charge.' Evidence: Claims 5, 6, 7, 8 and 13, all voted 3-0 on primary docs dated 2026-11-20. Quote: 'If you prefer a closed component composition, check out the snippet below.'
