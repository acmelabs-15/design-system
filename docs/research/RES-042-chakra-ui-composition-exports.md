# RES-042: How Chakra UI exports a convenience component beside its subcomponents

## Question
How does Chakra UI export a convenience component beside its subcomponents, and how do the subcomponents share state?

## Answer
Sufficient answer: facts about the current major version of Chakra UI, from its documentation and source, with the version named, covering the export shape (`X.Root`, `X.Item` and so on, shown on two or three components, one of them Steps); which components have a convenience component and where it lives (package or CLI snippets) and who owns it; the layers that share state among parts and what each owns; the documented means of custom composition and their named limits; how style reaches each part as far as it bears on composition; and whether components that are not built on Ark UI differ. Facts and sources only.

Version: Chakra UI 3 (`@chakra-ui/react` 3.38.0, main at commit 4d3fda5, 2026-11-11), built on `@ark-ui/react` 5.40.0, which uses `@zag-js/steps` 1.47.0.

1. **Export shape.** Each compound component is written as flat named React components (`StepsRoot`, `StepsItem`, `StepsIndicator`, ...). A `namespace.ts` file re-exports them under short names (`StepsRoot as Root`), and the component's `index.ts` exports both the flat names and `export * as Steps from "./namespace"`. So `Steps.Root` is an ES module namespace object, not a static property set on a function. There is no callable `Steps` component in the package: `Steps` is only the namespace. The same holds for Tooltip (Ark-based) and Card (not Ark-based).
2. **Convenience component.** The npm package has no convenience component for compound components. Chakra 3 moved away from "closed components" to "open, compound components by default". Convenience forms are **snippets**: source files in `apps/compositions/src/ui` (60 files) that `npx @chakra-ui/cli snippet add <name>` copies into the consumer's project (default `src/components/ui`). After the copy, the consumer owns that code. Chakra lists snippet changes in its changelog, and the consumer decides whether to update. The CLI skips existing files unless `--force` is given. A snippet may be a whole closed component (`tooltip.tsx` exports `Tooltip` with `content`, `showArrow` and `portalled` props). It may also be only some pre-assembled parts: `steps.tsx` exports `StepsItem` (Item + Trigger + Indicator + Status + Title/Description + Separator) and re-exports the raw parts, with no top-level `Steps` component. 27 component docs pages say "create a closed component composition" with a snippet. The Steps docs page has no snippet setup section, although the snippet exists in the CLI registry. Simple single components (Button, Badge, Spinner and others) are plain package exports with no namespace.
3. **Shared state (Ark-based components).** There are three layers, plus Chakra's style layer:
   - **Zag.js** (`@zag-js/steps`) owns the framework-agnostic state machine: step, count, linear and validation logic, events, and ARIA/keyboard behaviour. Its `connect(service, normalizeProps)` returns an API object with the current state and prop getters (`getRootProps`, `getItemProps(item)`, `getIndicatorProps(item)`, `getItemState(item)`).
   - **Ark UI** (`@ark-ui/react/steps`) owns the React binding. `useSteps` runs `useMachine` and `connect`. `Steps.Root` puts that API into a React context (`StepsProvider`). `Steps.Item` reads it and provides two more contexts: item props (index) and item state. Each part (Indicator, Trigger, Separator, ...) reads those contexts and spreads the matching prop getter onto its own element. `RootProvider` takes an external `useSteps()` result, so code outside the tree can control the component. `Steps.Context` and `Steps.ItemContext` (render props) and `useStepsContext` and `useStepsItemContext` (hooks) let custom parts read state.
   - **Chakra** wraps each Ark part. It adds no behavioural state. Its `createSlotRecipeContext` adds style contexts (see 5) and a `PropsProvider` context for default root props.
4. **Custom composition.** The documented means are: assembling the parts directly; `asChild` (Radix-inspired: the part merges its props and ref onto its single child element); the `as` prop (changes the element; TypeScript does not infer the target's props); Ark's `ark` factory; `Context` render props, `use*Context` hooks and `RootProvider` plus `use*` hooks; and the `ids` prop to share IDs when two components are composed. Named limits: the child must forward its ref and spread its props; `asChild` takes a single child only; some parts (for example `Checkbox.Root`, `RadioGroup.Item`) need specific child elements, and changing them must keep the result accessible; the `as` TypeScript caveat. Chakra's 3.24.2 changelog fixed `asChild` throwing on invalid children or `React.lazy` components (for example a Next.js `Link`). Chakra's parts pass `asChild` down to Ark (`forwardAsChild: true`). Ark then performs the child merge.
5. **Style per part.** Each component has one slot recipe (for example `steps`). The root (`withProvider`) runs the recipe with the variant props (`size`, `variant`, `colorPalette`) and puts the per-slot style objects and class names into two React contexts. Each other part (`withContext`) reads its slot from context. So a part takes its styles only inside its root. `unstyled` removes them, and `css` and `className` merge on top. A custom element passed through `asChild` receives the part's styles and class name. Table also offers `native`, which styles plain descendants with nested selectors.
6. **Components not built on Ark UI.** Alert, Blockquote, Breadcrumb, Card, DataList, EmptyState, List, Stat, Status, Table, Tag and Timeline use the same namespace export and the same slot-recipe contexts, but they wrap plain elements and have no state machine. Their parts share only style (and default props). The one exception found is Alert: it adds an `AlertStatusProvider` React context for `status`, which the indicator reads. Their convenience forms are also snippets (for example `alert.tsx` and `stat.tsx` are in the snippet directory).

UNVERIFIED / not confirmed: whether Chakra's GitHub issues name more `asChild` or composition limits beyond those in the docs and changelog (one developer-index search only). Chakra's Steps anatomy lists a `progress` slot, and Ark has `StepsProgress`, but Chakra's `Steps` namespace does not export `Progress`. Why is not documented.

- Chakra's `createSlotRecipeContext({key})` creates a styles context, a class-names context and a props context. `withProvider` (root) merges `PropsProvider` defaults with props, runs the slot recipe on the variant props, and provides styles and class names. `withContext` (other parts) reads `useStyles()[slot]` and the class name, and `unstyled` drops the slot styles. - Chakra's `chakra()` factory performs its own `asChild` merge (single valid child, merge props and refs) unless `forwardAsChild` is set. Source: packages/react/src/styled-system/factory.tsx:230-279 and components/steps/steps.tsx at the commit above, checked 2026-11-12.
- Chakra's composition docs name `as` (TypeScript does not infer the target's props) and `asChild` (inspired by Radix Slot), and the best practices "Forward Refs" and "Spread Props". Source: https://chakra-ui.com/docs/components/concepts/composition, checked 2026-11-12.
- Ark's composition docs: all DOM-rendering Ark components accept `asChild`; the `ark` factory; the `ids` prop to share IDs between composed components. Limitations: "pass only a single child element"; `Checkbox.Root` and `RadioGroup.Item` "have specific requirements for their child elements", and a changed element must stay accessible. Source: https://ark-ui.com/docs/guides/composition#limitations, checked 2026-11-12.
