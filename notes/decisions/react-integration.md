# Publish React support as a separate package

Provide React integration as a separate package around the same Lit components, using @lit/react where appropriate. Peter selected a separate package after the framework-package survey. Package names, peer-version ranges and release coordination remain for the inventory and migration plan.

React 19 supports custom-element properties and events directly. Wrappers are justified by typed JSX, event mapping and authoring consistency, rather than a claim that React cannot render custom elements. The approved custom-elements-manifest analyzer remains the metadata source; using a wrapper generator must not silently replace it with another analyzer.

For Table, the [clarified consumer-owned scope](tanstack-table-compatibility.md) keeps React cell rendering in the consuming React application. Our component must permit its content, events, references and layout to work correctly. A bridge that runs React cell components through TanStack's Lit renderer is not a selected requirement. Peter also explicitly confirmed TanStack Virtual for both React and Lit virtualization. Final composition still needs browser verification. Server rendering is excluded by the [server-rendering decision](server-rendering.md).

Evidence: [Lit practice review](../analysis/lit-practice-review.md#phase-1-extension-react-and-forms) and [package-layout survey](../analysis/repository-layout.md#phase-1-extension-framework-packages).

The selected declaration-order behaviour requires preserving the intended style-property order across complete React prop sets, including reorder-only renders and removals. The [initial source comparison](../alignment/evidence/declaration-order-probe-2026-09-20.json) is followed by [actual React execution](../alignment/evidence/style-input-integration-review-2026-09-20.json): with React/React DOM 19.3.0 and @lit/react 1.0.8, the plain wrapper passes 15 of 21 assertions; a wrapper synchronizing the complete style-input order passes all 21, both normally and in Strict Mode. Chromium, Firefox and WebKit produce the same results. The checks include refs, classes, slotted React child identity/state, event mapping, removal/re-addition and unmount.

This establishes a feasible order connection for two styling properties, not the final wrapper API or package certification. Actual package exports/types, compiler/manifest integration, all property kinds and the complete input-order contract remain to verify. Omitted CSS inputs follow the selected [undefined getter rule](layout-spacing-properties.md#omitted-styling-inputs-and-visual-defaults). No production wrapper or package was changed.

Peter subsequently selected the [Lit authoring helper](layout-spacing-properties.md#lit-helper-for-ordered-styling-inputs) as the corresponding complete-input path for Lit templates. Both paths retain the same component properties and canonical state. Coordinate their final input/removal/order contracts and types. The helper study also exposes a broader late-definition registry requirement at Lit node creation; [global-registry results](../analysis/lit-practice-review.md#lit-helper-lifecycle-and-registry-boundary) do not certify scoped registries or adopted documents for either framework path.

The selected [helper ownership and reassertion rules](layout-spacing-properties.md#external-writes-to-helper-managed-settings) preserve that framework consistency: managed inputs are reapplied on helper renders, matching the tested React wrapper's full-prop writes; direct component-property edits remain effective until a subsequent wrapper/helper render. Unrelated inputs are not automatically cleared by adopting the Lit helper. Final cross-framework types and complete removal/ownership behavior still need acceptance; these choices do not certify all React paths.
